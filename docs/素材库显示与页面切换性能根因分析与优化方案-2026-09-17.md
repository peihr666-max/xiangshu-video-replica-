## 一、素材库显示问题的根因（5 条）

### 1.1 每页只显示 6 条（`pageSize = 6`）

`client/src/studio/ContentPages.tsx:68`：

```ts
const pageSize = 6;
```

素材库、发布管理等内容页共用该常量。一屏 6 条 + 密集分页按钮，素材稍多就显得"显示不全/有问题"。服务端上限是 100（`server/app/material_routes.py:43-61`），前端却只取 6。分页器还把全部页码按钮一次性渲染（ContentPages.tsx:2419-2429），素材到几百条时页码按钮本身也是渲染负担。

### 1.2 视频素材没有缩略图：靠整段视频流经服务端代理出首帧

`MaterialItem` 模型只有元数据，**没有任何 url / thumbnail 字段**（`server/app/materials.py:102-127`）。前端瓦片对视频素材的渲染是：

- `client/src/studio/ui.tsx:338-362`：`<VideoPreview src={asset.url}>`，无 url 时显示「视频预览图」文字占位（ui.tsx:354-360）；
- `client/src/VideoPreview.tsx:195-216`：`<video preload="metadata" src={签名URL}>`。

而 `asset.url` 来自逐条请求换来的签名代理 URL。也就是说：**网格里每个视频瓦片都要让浏览器通过 FastAPI 服务端代理（`GET /api/assets/signed-objects/...`，media_routes.py:816-825）去拉视频元数据/首帧**。每页 6 个视频 = 6 路经服务端转发的视频流，只为出一张封面。服务端虽支持 Range（media_routes.py:531-568），但带宽和并发都压在应用服务器上，瓦片出图慢、黑块多。

### 1.3 每个瓦片 2 次 N+1 请求才能显示

`client/src/studio/ContentPages.tsx:2075` 对本页全部素材循环 `loadPreview(asset)`；`loadPreview`（ContentPages.tsx:1858-1935）→ `getMaterialCachedPreview`（api.ts:4498-4528）每个素材固定发：

1. `POST /api/assets/{id}/download-url` —— 服务端**占用一个写库连接、写一条审计记录**后才签出 15 分钟有效的代理 URL（`server/app/rbac_routes.py:930-998`）；
2. `GET /api/assets/{id}` 元数据；
3. 图片类再拉字节（视频在播放时拉）。

6 条/页 = 每次进素材库至少 12+ 个请求；启动时后台还预取了 60 条元数据（live.ts:1164-1167）。本机 CacheStorage 字节缓存命中也**照样要先发授权请求**（api.ts:4518 注释 "Fresh authorization is required even when every media byte is already local"）。

### 1.4 失败/超时的瓦片永久空白，只能点击或重进页面恢复

- `loadPreview` 早退守卫（ContentPages.tsx:1860-1865）：已在加载或已失败不自动重试；失败只置 `{status:"error"}`（1916-1927），**唯一重试入口是用户点击瓦片**（2389-2391）。
- 全局请求超时 5 秒（api.ts:6），素材预览属普通请求通道；云环境稍慢即批量超时。
- `VideoPreview` 的 poster `onError` 一旦触发**永久置灰**「预览图暂不可用」，不重新签名（VideoPreview.tsx:235-238）。
- 签名 URL 有效期仅 **15 分钟**（rbac_routes.py:61，过期 403 于 media_routes.py:391-420）：页面停留超 15 分钟后图片/视频集体失效，重进页面（重新签名）才恢复——这正是"需要再次加载"的时间相关版本。

### 1.5 素材库全部状态是页面组件局部 state，切页即丢

`previewStates/remotePage/...` 全部是 `MaterialsPageContent` 的 useState（ContentPages.tsx:1769-1801）。切到别的 tab 再切回来，整个组件卸载重挂：重新 listMaterials + 重新逐条签名 + 重新出图。图片字节虽有 CacheStorage 缓存，但授权请求照样全量重发（1.3），观感就是"每次进素材库都要等一轮"。

**对照（仓内正面案例）**：爆款视频封面走 `/api/viral/covers/{platform}/{video_id}`——确定性 key、免登录、`Cache-Control: public, max-age=604800` 7 天浏览器缓存（server/app/viral_routes.py:468-504）。同一个仓库里已经存在"稳定封面 URL + 浏览器缓存"的正确范式，素材库完全可以对齐。

## 二、所有页面首开内容缺失、需二次加载的根因（5 条）

### 2.1 启动加载是"一次性 allSettled，失败降级为空、无自动重试"

工作区挂载时 `loadStudioData` 一次并发 9 组请求（项目+8 个预览 URL、人物、生成批次 20、stats、analytics 7/30、口播 20、爆款 2 平台、素材 60）（`client/src/studio/live.ts:1054-1080`）。任何一组 reject，对应数据**保持空数组**，只往 `errors` 数组塞一条文案：

```ts
// live.ts:1121-1123
// 素材库加载失败不打断工作区：视频生成页的选择器退化为仅已加载资产。
const materials = materialsResult.status === "fulfilled" ? materialsResult.value : [];
```

之后没有任何 per-slice 重试；唯一恢复入口是顶部 banner 的「重试加载」整页重来（StudioWorkspace.tsx:1948-1954），或者重开页面触发重挂载。**"内容没显示 → 切走再切回来就有了"的直接机制。**

### 2.2 5 秒全局硬超时 × 20–40 个扇出请求 = 必有失败面

`REQUEST_TIMEOUT_MS = 5_000`（api.ts:6）作用于所有普通请求。启动风暴里任何一个请求慢于 5 秒，该切片即失败并按 2.1 降级为空。没有任何调用方消费响应里的 `retryable` 字段（api.ts:5150-5166 有标记、无重试）。

### 2.3 客户通道首开 double bootstrap：第一遍全量加载被丢弃

profile 异步到达后 `display_name`/`username` 从回退值变为真实值（customerToCurrentUser.ts:22-23）→ `workspaceUser` memo 变化（StudioWorkspace.tsx:263-276）→ 依赖它的 bootstrap effect（1051-1099）**完整重跑一遍 loadStudioData**。首屏实际等待第二遍，第一遍的几十个请求全部作废，同时把 2.2 的超时失败面翻倍。

### 2.4 大量静默吞错：用户看到空白且无提示

- 恢复云端草稿/我的文案：`loadSavedScriptList().catch(() => [])`、`.catch(() => {})`，注释明写"失败静默"（StudioWorkspace.tsx:643-666）→ 文案工坊首开空白；
- 爆款区 `.catch(() => {})` 连 errors 都不入（1093-1095）；
- 素材/人物预览 URL `.catch(() => undefined)`（live.ts:1183-1234）→ 无预览图、无提示。

失败后无重试、无错误态，直到重挂载才可能成功。

### 2.5 会话/人物等一次性守卫，失败不重试

- 会话自恢复 `bootstrappedRef` 只跑一次（useCustomerSession.ts:316-359），瞬时失败直接落登录/激活页；
- 人物场景照 `loadedPeopleRef` 守卫（StudioWorkspace.tsx:1137-1147）；
- 人物加载本身是**逐人串行 for 循环**，每人 3 组请求（头像签名、五视图、口播 avatars/voices）（live.ts:668-680），8 人就是 24-48 个串行请求——首屏最慢的一环，任一失败该人物 `portrait: undefined` 无图。

## 三、页面切换迟钝卡顿的根因（6 条）

### 3.1 切 tab = 卸载重挂 + 每页重新拉全量数据（卡顿主因）

页面按 `state.page` switch 条件渲染（StudioWorkspace.tsx:2164-2221），一次只挂载一页本身没问题；问题是**每个页面组件把数据请求放在 mount effect 里且无页间缓存**，每次切入都重跑：

| 页面 | 每次切入重发的请求 | 证据 |
|---|---|---|
| 视频创作 | 分镜/拆解/提示词/文案版本 4 并行 + 报价 | CreationPages.tsx:1374-1380、1480-1483、1506+ |
| 爆款视频 | 平台列表 + 每条视频统计 | ContentPages.tsx:206-246、808-818 |
| 素材库 | listMaterials + 逐条预览签名 | ContentPages.tsx:2017-2045、2075 |
| 发布管理 | 草稿→逐素材签名→云发布账号；内嵌面板再拉发布记录 | ContentPages.tsx:2780-2893、PublishRecordsPanel.tsx:90-99 |
| 数据看板 | **无视 context 已有 analytics 仍重拉** getStudioAnalytics+Stats | AnalyticsPage.tsx:166-218 |

切页的体感 = 白屏/骨架 → 一轮网络等待 → 内容渐进补齐，即"迟钝"。

### 3.2 单一巨型 context + 全库 0 处 memo：任何 setState 全树重渲染

`StudioContext` 未拆分（context.tsx:4-9），value 每次渲染重建（StudioWorkspace.tsx:1768-1791），包住整个 shell（1827）。StudioWorkspace 内约 40 个 useState，全代码库 grep `memo(` 为 0。于是：

- 20 秒任务轮询每次 `setData`（三请求：retryWallet + 两个 list + stats）→ 整个工作区 + 当前页全量重渲染（StudioWorkspace.tsx:1106-1132）；
- 页内 1 秒 tick（VideoResultStage.tsx:21,144）、6 秒 tick（CreationPages.tsx:2921-2929）持续制造全树渲染。

### 3.3 常驻轮询不休眠

任务轮询有 `document.hidden` 检查（1109），但 30 秒通知轮询（WorkspaceNotifications.tsx:26-53）和 30 秒心跳（useCustomerSession.ts:461-475）**没有**——后台挂着也一直打。

### 3.4 单 JS 包 692KB，无页面级代码分割

全部页面在 StudioWorkspace.tsx:28-107 静态 import；全 src 仅 RootApp.tsx:17-25 两处 lazy；vite.config.ts:105-123 无 manualChunks。本地 dist（9 月 6 日构建）为单个 692KB JS + 184KB CSS。首次解析成本集中，切页虽不用重新下载，但低端 Windows 机器（Tauri WebView）上大 bundle 的交互建立成本可感。

### 3.5 重资源不懒加载

1.64MB 的 `activation-background-*.png`（登录/激活背景）与 150KB logo 直出；32 处 `<img>` 仅 5 处 `loading="lazy"`。

### 3.6 dev 环境放大器（仅开发模式）

StrictMode effect 双跑（main.tsx:18）+ useCustomerSession 注释明说 boot effect 双份（useCustomerSession.ts:312-388）——开发时首屏请求量翻倍，所有上述问题在 dev 观感更重。生产无此项，但**不能用它解释生产卡顿**。

## 四、优化方案

### P0 —— 直接对症、小改动大收益（建议 1-2 个任务）

| # | 改动 | 位置 | 预期收益 |
|---|---|---|---|
| P0-1 | 素材库 `pageSize` 6 → 24；分页按钮窗口化（前后各 2 页 + 省略号） | ContentPages.tsx:68、2419-2429 | 素材库"显示不全"观感直接消除 |
| P0-2 | **批量预览授权**：新增 `POST /api/assets/download-urls`（body: asset_id 列表 ≤100），服务端一个写事务签出整页 URL；前端 listMaterials 返回后一次调用替换逐条签名 | server/app/rbac_routes.py、client/src/api.ts、ContentPages.tsx:2075 | 每页 N+1（12+ 请求）→ 2 请求；写库连接/审计写入从每瓦片一次降为每页一次 |
| P0-3 | **视频缩略图**：素材归档时抽首帧存 COS（缩略图对象），列表返回 `thumbnail_url`，走稳定路由 + `Cache-Control` 长缓存（**照抄 viral covers 范式** viral_routes.py:468-504）。短期兜底：视频瓦片未拿到缩略图前不渲染 `<video preload>`，显示统一占位 | server/app/materials.py、material_routes.py、新抽帧逻辑（ffmpeg 已随 NSIS 分发）、ui.tsx、VideoPreview.tsx | 素材库视频瓦片秒出封面；服务端不再为网格转发视频流 |
| P0-4 | 预览失败自动重试：error 瓦片自动重签 1-2 次（指数退避）；`onError` 收到 403/过期时重签一次而非永久置灰 | ContentPages.tsx:1858-1935、VideoPreview.tsx:235-238 | "空白瓦片要点击/重进才恢复"消除 |
| P0-5 | 消除 double bootstrap：bootstrap 依赖收敛为 `user.id`（+ token epoch），display_name 变化不触发全量重载；或 profile 到达前不发第一遍 | StudioWorkspace.tsx:263-276、1051-1099 | 首屏请求量减半、就绪时间近似减半 |
| P0-6 | 超时分层：启动批量接口（listMaterials/loadStudioData 各组）用 15s 超时（复用 CLOUD_OP_TIMEOUT_MS 通道或新增 BOOTSTRAP_TIMEOUT），失败切片自动重试一次 | api.ts:6-9、live.ts:1054-1080 | 5 秒硬超时造成的"首开空切片"大幅减少 |

### P1 —— 结构性：页间缓存 + 渲染治理（解决卡顿主体）

| # | 改动 | 位置 | 预期收益 |
|---|---|---|---|
| P1-1 | **页间数据缓存（stale-while-revalidate）**：素材列表/爆款列表/看板/发布记录的页级 fetch 提升为模块级缓存 store——切回页面先渲染缓存、后台静默刷新。不引第三方库，仿 api.ts:2343 `generationReconcileWaiters` 的模块级去重先例 | 各页 mount effect + 新 `studio/pageCache.ts` | 切页从"白屏等网络"变"立即出内容"；这是"卡顿"体感的最大单项 |

| P1-3 | Context 拆分 + memo：高频切片（tasks 轮询、previewStates、tick 类）与低频（user/capabilities/navigate/notify）拆成两个 context；任务表/素材网格等列表组件 `React.memo` | context.tsx、StudioWorkspace.tsx:1768-1791 | 20s 轮询不再全树重渲染；1s tick 局部化 |

| P1-5 | 轮询治理：通知/心跳补 `document.hidden`；任务轮询按需变频（有 running 任务 10s，空闲 60s） | WorkspaceNotifications.tsx:26-53、useCustomerSession.ts:461-475、StudioWorkspace.tsx:1106 | 空闲时请求量与重渲染大幅下降 |
| P1-6 | 大图优化：activation-background 转 WebP/压缩（1.64MB → 预计 <200KB）；其余 27 处 `<img>` 补 `loading="lazy"` | assets、各组件 | 登录/激活页首屏明显加快 |

### 实施约束（按仓库协作规则）

- 以上任一改动开工须走 AGENTS.md 流程：认领登记 → 独立 worktree → 从最新 origin/main 建分支 → 测试先行（红→绿）→ 三门禁 → PR。建议切分为：**任务 A**（P0-1/2/4，前后端各一 PR 或按改动范围合并）、**任务 B**（P0-3 缩略图，含 ffmpeg 抽帧与 COS key 规范，需迁移登记）、**任务 C**（P0-5/6 + P1-1/2 启动与缓存）、**任务 D**（P1-3/4/5 渲染与打包）。
- P0-2/P0-3 动服务端接口与响应模型：需同步 `client/src/generated/api` 类型与 e2e 契约测试；素材列表内联/批量签名涉及越权面，测试须覆盖跨用户访问拒绝；审计口径变化需与现有审计约定核对。
- P0-3 涉及历史素材无缩略图的兼容（懒生成或占位降级）。

### 验收口径（建议）

1. 素材库首屏：列表 1 请求 + 批量签名 1 请求，全部瓦片 ≤3 秒出封面（含视频缩略图）；失败瓦片 5 秒内自动恢复，无需点击/重进。
2. 全站切页：命中缓存时无网络等待直接出内容，后台刷新静默完成；网络面板确认切回已访问页不再重发全量列表请求。
3. 启动：bootstrap 请求总数从约 40 降至 ≤15（消 double bootstrap + 批量签名 + 人物并发化后），无"空切片需重进页面"。
4. 空闲（无 running 任务、页面隐藏）时请求速率≈0。

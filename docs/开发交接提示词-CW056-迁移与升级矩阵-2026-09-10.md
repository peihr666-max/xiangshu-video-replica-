## 8. 必踩的坑

1. **PG 容器串台**：忘导 `TEST_POSTGRESQL_URL` → `pg_test_kit.py:32` 与 `test_postgres_migrations.py:27` 的默认 DSN 都指向 **5433**，你会打到 CW-055/CW-031 或主工作区的容器上。**你的测试会 `DROP DATABASE … WITH (FORCE)`，串台等于删别人的库。每开一个新 shell 先 `echo $TEST_POSTGRESQL_URL` 确认是 5436。**
2. **`scripts/pg-fixture.sh stop/clean` 是全局破坏**：容器名硬编码。收尾只 `docker stop cw056-pg-test`。
3. **`downgrade base` 会删光所有表**：`_rehearsal_dsn()` 的 docstring 就是这么写的（L202）。**绝不要**在共享库 `customer_v3_test` 上跑 downgrade 演练——必须用专属库（现有代码用 `t06_migrate_test`，你新增的矩阵用 `cw056_head_*_test`）。
4. **`alembic_version.version_num` 宽度陷阱**：Alembic 建 VARCHAR(32)，本项目 revision id 达 33+ 字符（如 `017_generation_task_retry_lineage`）。`env.py:59-81` 的 `widen_postgres_version_table()` 是既有修复，**online 路径有效，offline 路径无效**（这就是 M7 限制、也是 §5.4 水印的技术依据）。矩阵里每个起点升级后都要断言 `version_num` 完整未被截断。
5. **`env.py:118` 的显式 `connection.commit()` 不是 bug**：注释说明——不 commit 的话连接停在隐式 autobegin 事务里，Alembic 复用该「外部」事务，整条升级链在连接关闭时被回滚。**别当冗余代码删掉。**
6. **`migrate.sh:25` 的 `exec` 会让失败无法捕获**：`exec flock -n … alembic upgrade head` 用 alembic 进程替换 shell，`set -e` 之外的任何后置校验都不会执行。§5.6 第 4 项要求去掉 `exec`，这是本文件最重要的改动。
7. **哈希冻结 vs 追加迁移的冲突**：如果你必须追加修复迁移（§6 第 7 步），`FINAL_HEAD` 会变，`alembic heads` 会变，`HEAD_REVISION`（L31）会变，**9 处 `assert version == HEAD_REVISION` 依赖此值**（L29-31 注释明写）。追加时：新 revision 的哈希**手工追加**到 JSON，旧 79 个哈希**一个字节都不能变**，`FINAL_HEAD` 与 `HEAD_REVISION` 同步更新，并在 PR 里显式说明「本次追加了 N 个修复迁移，已发布 revision 哈希未变」。
8. **严禁两个全量 pytest 同时打同一 PG fixture**：AGENTS.md 记录 2026-08-23 T19 实测教训——5 个测试文件共享 `customer_v3_test`，并发互踩造成假性失败。你的矩阵测试尤其危险（大量 CREATE/DROP DATABASE）。独立容器解决了跨 Agent 互踩，但**同一 Agent 内不要并行开两个 pytest**，矩阵参数化用例也**不要**用 `pytest-xdist` 并行（DROP DATABASE 会互相 FORCE 掉对方正在用的连接）。
9. **陈旧连接池污染**：CW-025 修过一个根因——`test_internal_access_tokens.py` 的 module-scope fixture teardown 只 drop DB 没调 `close_pg_pool()`，陈旧池单例按文件字母序（i < p）污染 `test_postgres_migrations`。**你新增任何 module/session scope 的 PG fixture，teardown 必须调 `close_pg_pool()`。**
10. **`RECORDED_TEST_DATABASES` 白名单**：新建库必须先登记，否则 `assert_safe_test_database()` 直接 `PgPreflightError`（错误信息会明确告诉你要去 `pg_test_kit.py` 登记）。你独占该文件，但**登记动作要在写测试之前**，否则第一跑就是 preflight 失败而不是你以为的迁移失败。
11. **CI 的 PG 与本地不同源**：Linux quality gate 用 GitHub Actions 的 `postgres:16` service 并设 `TEST_POSTGRESQL_URL`（`test_postgres_migrations.py` L6-8 docstring 明写）。**本地端口方案（5436）不影响 CI**，不要把 5436 硬编码进任何测试或脚本。
12. **本地跑不到的四项**：`cargo test`、`npm audit`、客户浏览器 E2E、`npm run build` 的 CI 完整链路 —— 只在 CI 三门禁执行。你新增的 CI step（§5.5 第 4 项）**本地可以先跑** `python scripts/verify_migration_hashes.py` 验证。
13. **Node 版本**：见 §2.3，收尾跑 `npm run check` 前忘加 PATH 前缀 → vitest 全崩且看起来像「没有测试」。
14. **`npm run check` 末尾含服务端全量 pytest**（账本口径 1446+ 用例，21–30 分钟），**每任务只跑一次**，在收尾时跑。你的矩阵测试会显著增加耗时（5 个起点 × 完整升级链 × 2 份 schema 目录导出），**先在专项里测出矩阵耗时并写进证据文件**，避免收尾时超时误判。

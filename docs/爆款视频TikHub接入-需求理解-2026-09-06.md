# 爆款视频页（C4 重启）· TikHub 接入需求理解与接口实测

> 2026-09-06 · 基于用户需求口述 + TikHub 官方 OpenAPI 实测（真实测试 key 由用户提供，**不入库、不进代码**）+ 视频号解密算法研究与字节级验证。
> 背景：C4「爆款视频参考库」此前用户决策暂缓（爆款页保持空态，`live.ts` `videos: []`）；本轮重启，接入抖音 + 视频号两个平台的真实搜索数据。
> 2026-09-06 晚更新：用户已对 7 个决策点拍板（见 §六），视频号解密算法已完成研究与验证（见 §五）。

## 一、需求原文归纳（用户口径）

1. **标签展示**：根据提示词返回的标签进行显示，最多显示 6 个标签。
2. **视频卡片优化**：
   - (a) 以竖屏为主，每排放 4 到 5 个视频；
   - (b) 返回数量按 API 实际返回定（抖音约 20；视频号 30，翻页聚合）；
   - (c) 卡片内容根据视频号或抖音号返回的数据来生成。
3. **视频详情**：根据返回的字段重新设计显示。
4. **视频文件策略**：分辨率选最低即可；确认返回的是加密视频还是可播放视频（抖音返回的可以用）；**有音频优先用音频，没有就用低分辨率视频**；视频均需为**最近 7 天**爆款。

## 二、接口选型结论（实测）

| 平台 | 选定接口 | 排除项及原因 |
| --- | --- | --- |
| 抖音 | `POST /api/v1/douyin/search/fetch_general_search_v2`（综合搜索 V2） | `fetch_video_search_v3` 实测一次返回 1000 条榜单池、字段弱（无评论/转发/收藏）、无翻页游标 |
| 视频号 | `POST /api/v1/wechat_search/v2/fetch_search_videos`（搜一搜·视频号视频） | `wechat_channels/v2/fetch_search_channel_videos` 是**号内搜索**（需指定创作者），不适用于关键词爆款池 |
| 视频号媒体 | `POST /api/v1/wechat_channels/v2/fetch_video_detail`（`raw=false`） | 仅在需要媒体文件（提取文案/复刻）时调用，见 §五 |

**请求参数与页面交互映射**

- 抖音：`keyword` + `sort_type`（0=综合 **1=最多点赞** **2=最新发布**）+ `publish_time`（**固定 7=最近一周**）+ `content_type`（固定 1=只搜视频）+ `filter_duration`。
- 视频号：`keyword` + `sort`（default=相关 **hot=点赞降序** / **latest=最新**）+ `publish_time`（**固定 week=最近七天**）+ `offset`/`cursor` 翻页。
- 排序控件映射："热门优先/最新" → 抖音 `sort_type=1/2`；视频号 `hot/latest`。均实测有效。

## 三、实测数据与关键修正

> 测试关键词「乡墅」，2026-09-06，全部 HTTP 200。

### 3.1 抖音（一次调用）

- **单次返回卡数浮动**：不限时间 19 卡（17 视频 + 2 张"相关搜索词"卡 type=6，需过滤）；**最近 7 天 + 最多点赞 → 仅 5 条**。数量完全随关键词池浮动，"约 20 个"只是不限时间下的表现；**服务端关键词配置应选宽词**（如"别墅""自建房"），避免列表过稀。
- 翻页：响应 `extra.search_request_id`/`logid` 可作下次请求 `search_id`，本期不做。
- **视频字段**（`data.business_data[].data.aweme_info`，type=1）：
  - `aweme_id`、`desc`（标题，内嵌 #标签文本）、`create_time`（unix 秒）
  - `text_extra[]` → `hashtag_name`（结构化标签）→ **标签上限 6 的数据源**
  - `video.cover.url_list[0]`（image/webp 可直连）、`video.width/height`（576×1024 / 720×1280，**全竖屏**）、`video.duration`（毫秒）
  - `statistics`：digg/comment/share/collect；**play_count 在搜索响应恒为 0（播放量拿不到）**
  - `author`：nickname、avatar url、is_verified、signature
  - `music.title`、`music.play_url.url_list`（原声 mp3 直链，见 §五.3）

### 3.2 视频号（每页 10 条，翻 3 页聚合 30 条）

- **实测每次调用返回 10 条**（默认/热门排序均为 10），与最初"一次 15"的预期不符；**用户已确认按 3 页 × 10 聚合 30 条**（拿上一页 `data.cursor` 回传，`continue_flag=1` 继续、`no_more` 提前停）。
- 7 天筛选（`publish_time=week`）实测正常（total=230，池子足够）。
- **搜索条目字段**（`data.results.data[0].subBoxes[].items[]`）：
  - `title`（**内嵌 `<em class="highlight">` 高亮标记，必须清洗**）、`duration`（"00:11" 字符串）、`width/height`（1080×1920 标称，**CDN 实际下发 576×1024 变体**）
  - `image`（封面，image/jpg 可直连）、`likeNum`（**字符串**："6391"/"10万+"，排序需解析）、`pubTime`（unix 秒）+ `dateTime`（"20小时前"）
  - `source.title`（作者昵称）、`source.iconUrl`（作者头像）、`docID`/`exportId`
  - **搜索结果无标签、无评论/转发/收藏数**；标签从标题 `#` 分段解析。
- **详情**（`fetch_video_detail` + `exportId`，exportId 会过期需及时用；响应慢要求 30s 超时；计费 $0.01/次）：`object_id`、`title`/`description`、`like_count`/`fav_count`/`forward_count`/`comment_count`（数值）、`create_time`、`location.city`、`nickname`、`username`(@finder)、`media{full_url, decode_key, cover_url, duration, width, height, md5, file_size}`。

### 3.3 详情页数据源结论（决策点 ⑤ 已拍板）

对照详情页显示需求：**搜索结果字段已满足展示要求**——标题、作者（昵称+头像）、发布时间、时长、点赞、封面、宽高、标签（标题解析）全部齐备；缺的仅是评论/转发/收藏数与城市（非必需展示项）。

**方案**：进入详情页**不实时调详情接口**；仅在用户点击「提取文案 / 视频复刻」（需要媒体文件 full_url + decode_key）时实时调用。抖音搜索结果自带全部展示字段与可播 URL，任何场景都无需详情调用。

### 3.4 "最近 7 天"固定筛选

抖音 `publish_time=7`、视频号 `publish_time=week`，均已实测生效。

## 四、卡片与详情页设计映射（平台字段 → UI）

**列表卡片（两平台通用结构，字段按平台取值）**
1. 封面（抖音 `video.cover` / 视频号 `image`），竖屏 9:16 裁切，角标时长；
2. 标题（抖音 `desc` / 视频号清洗后 `title`），两行截断；
3. 作者行：头像 + 昵称（+ 抖音认证标）；
4. **标签 ≤6**：抖音 `text_extra.hashtag_name`；视频号标题 `#` 分段解析；
5. 数据行：点赞（视频号 `likeNum` 字符串直显，排序时解析）；
6. 平台角标（抖音/视频号）+ 收藏/复刻入口。

**网格与分页（决策点 ⑥ 已拍板：滚动加载）**：竖屏卡 4 列起步（宽屏 ≥1600px 升 5 列）；抖音一次调用一批（5–19 条浮动），视频号聚合 3 页 30 条；滚动到底触发加载下一批。

**详情页**：标题、标签（≤6）、作者卡（头像/昵称/认证/签名）、发布时间、时长、点赞（+抖音的评论/转发/收藏）、封面；抖音可直接 `<video>` 播 540p，视频号预览经解密后播放（见 §五），未解密时回退封面 + 提示。操作区沿用：提取文案（音频优先管线）/ 视频复刻 / 收藏。

## 五、视频号解密研究结论（决策点 ①④ 已完成研究）

### 5.1 加密机制（实测 + 开源逆向分析双重确认）

- 微信视频号仅加密 MP4 **前 128 KB（131,072 字节）**，其余为明文；
- 用 API 返回的 `decode_key`（十进制字符串，即 uint64 种子）作为 **ISAAC64 PRNG** 种子生成 131,072 字节密钥流；
- 密钥流与文件前 128 KB **XOR** 即完成解密，其余原样保留；
- `decode_key` 每次请求都会变化，**必须使用同一响应里的 key**。

### 5.2 算法已字节级验证（本仓库可直接落地）

- 参考实现：社区 Go 移植（JohnABC/WechatSphDecrypt `decrypt.go`，Jenkins 原版 ISAAC64）与微信官方 WASM 模块（evil0ctal 仓库 `wasm_video_decode.wasm`）**输出逐字节一致**；
- 我们已用纯 Python 复刻同一算法，对两个不同 decode_key 生成的密钥流与 WASM 输出**全量比对通过**，并用其解密了两个真实加密视频（11.9s 与 52.3s，ffprobe 确认 h264+aac、可播放）；
- 算法要点（实现规约，写代码时以此为准）：
  - 种子：`Seed[0] = uint64(decode_key)`，其余 255 词为 0；
  - randinit：`a..h = 0x9e3779b97f4a7c13`，mix 4 次；两轮循环（先加 Seed 词、后加 MM 词）各 32 次 mix 写入 MM；
  - 每轮生成 256 词；**词按索引逆序消费（Seed[255]→Seed[0]），每词按大端输出 8 字节**；
  - mix 八元组轮转（64 位）：`a-=e; f^=h>>9; h+=a; b-=f; g^=a<<9; a+=b; c-=g; h^=b>>23; b+=c; d-=h; a^=c<<15; c+=d; e-=a; b^=d>>14; d+=e; f-=b; c^=e<<20; e+=f; g-=c; d^=f>>17; f+=g; h-=d; e^=g<<14; g+=h`（**注意与 32 位 ISAAC mix 不同，勿混淆**）；
  - 主循环位移：`^(a<<21)` 取反、`>>5`、`<<12`、`>>33` 按 i%4 轮替；
  - 性能：纯 Python 生成 128KB 密钥流约 **12ms**，可忽略；实现时放服务端，密钥流可按 decode_key 做进程内 LRU（收益小，可选）。

### 5.3 最佳方案（回答决策点 ①"不落盘、直接解密后储存到云储存"）

**可行，且推荐纯服务端内存流式管线，无需本地磁盘、无需 Node/Docker 依赖：**

```
TikHub fetch_video_detail (raw=false)
  → media.full_url + decode_key
  → HTTP 流式下载（requests stream）
  → 前 131072 字节：Python 生成密钥流(≈12ms) + XOR（内存内完成）
  → 其余字节：原样透传
  → COS 分块直传（cos-python-sdk-v5 流式上传，内存占用=分块大小）
```

- **不落盘**：只有前 128KB 在内存中变换，整个文件无需写本地磁盘；
- **加速**：解密开销 ≈12ms + 128KB XOR（<1ms），总耗时基本等于下载耗时；可并发多视频管线；
- **存储即成品**：解密后的无水印可播 MP4 直接进 COS，前端 `<video>`/复刻/文案提取均走 COS URL（配合现有 COS 归档质检链路）；
- **校验**：TikHub `media.md5` 与 CDN 下发文件 md5 不一致（CDN 给的是转码变体，`file_size` 13.97MB vs 实际 2.97MB），不能用作解密校验；以「前 8 字节 == ftyp box」+ ffprobe 抽检代替；
- **备注**：视频号无音频直链（`audio_url` 恒空）→ 音频提取统一走"解密后 MP4 → 本地 ffmpeg 抽音轨"（与抖音无原声视频的兜底路径一致）。

### 5.4 抖音侧媒体策略（实测）

- `video.bit_rate[]` 多档分辨率中**取高度最小档（实测 540p = 576×1024）**：HTTP 206 + `ftyp isom` 标准 MP4，**无加密、可直接播放**；
- **音频优先**：`music.play_url` 对原声视频给出 mp3 直链（实测 17 条中 15 条可用，content-type `audio/mpeg`）；平台 BGM 类视频无音频链 → 540p 视频兜底；
- 「提取文案」管线：有 `music.play_url` → 直接下 mp3；否则下 540p mp4 → ffmpeg 抽音轨。

| # | 决策点 | 结论 |

## 九、2026-09-06 追加需求与修正规约

本节按同日后续用户指令更新 §3.3、§5.4 和决策点 5，历史实测保留用于追溯。

### 9.1 数据库是列表与反馈的数据来源

- 新增迁移 `062_viral_video_library`，搜索结果写入 `viral_videos`，以平台和视频 ID 去重；历史记录保留，列表筛选最近 7 天。
- `viral_fetch_state` 记录平台、排序及分类的拉取时间。列表缓存 1 小时；命中时读库，不请求数据源。到期才刷新并 upsert，然后从数据库返回。
- 分类请求可以并行；视频号同一分类的 cursor 依赖上一页，3 页必须顺序获取。一类失败仍保存其它类的成功结果，失败类冷却 1 分钟再重试。
- 列表响应新增 `source="database"`、真实 `fetchedAt`、`stale`，刷新失败有旧数据时返回旧数据且标记过期。没有配置数据源时仍允许读取已保存条目和媒体。
- 同一桌面服务进程对回源与媒体下载合并重复请求；多进程部署的分布式互斥尚未实现。

### 9.2 视频号四项统计独立补采

用户明确要求列表页显示真实评论、转发和收藏。因此，可见的视频号条目会调用 `POST /api/viral/videos/statistics`，请求体 `{videoIds: string[]}`（1–12 条），响应 `{items: ViralVideoItem[]}`。

| 展示字段 | 详情响应字段 | 数据库列 |
| --- | --- | --- |
| 点赞 | `like_count` | `likes` |
| 评论 | `comment_count` | `comments` |
| 转发 | `forward_count` | `shares` |
| 收藏 | `fav_count` | `collects` |

- 只查询已入库的视频号条目，最多 3 个并发详情请求，数据库串行回写；不因统计补采下载视频。
- 成功结果缓存 24 小时，失败冷却 10 分钟。搜索刷新保留统计缓存时间，但更新最新 `exportId` 配对。
- 缺失字段为 `null`，界面显示 `—`；真实数值 `0` 保留。部分响应不覆盖已有有效统计，四项全缺失不记录成功时间。
- 内部缓存时间不进入客户响应。媒体首次获取时已经取得的统计也回填数据库。
- 实际样本核对：同一视频详情返回点赞 6947、评论 114、转发 5861、收藏 6378，已逐字段保存并通过列表响应读回。

### 9.3 原位播放与单视频播放

- 两个平台点击卡片播放都走服务端媒体缓存接口，返回浏览器可用的地址。抖音选源需排除 ByteVC 编码档，不能只取最低分辨率；旧不兼容缓存与浏览器缓存使用不同对象键。
- 卡片保留原生播放器控件，支持暂停、继续、进度与音量。播放时收起覆盖控件的统计和作者浮层。
- 页面只允许一条视频播放；点击另一条立即暂停当前条目，旧异步请求晚到也不能抢占。暂停保留播放进度，再次继续不重复获取媒体。
- 媒体请求超时 120 秒，首次需要下载时显示准备状态；已保存媒体复用存储，不再次调用详情或下载源文件。

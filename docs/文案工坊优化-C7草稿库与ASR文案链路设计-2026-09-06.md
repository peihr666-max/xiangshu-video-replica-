## 2. C7 草稿库设计

### 2.1 为什么不复用 `/projects/{id}/scripts`

1. scripts 表是项目维度，从爆款视频/人物库进入文案工坊的草稿没有 `projectId`；
2. 语义冲突：旧工作区按《工作区交互契约》把 `scripts/latest` 当"口播稿已保存版本"门禁消费（stale 稿视为缺失、未保存禁止编译 Prompt）。草稿自动保存若直写该表，未确认草稿会泄漏进生成门禁，破坏 fail-closed 语义。

### 2.2 表结构（新迁移 `058_studio_drafts`；追加式，不碰冻结名单 025–030；同步 bump 三处 head 断言 057→058）

```sql
-- 工作草稿：每用户每工作区一行，自动保存 upsert
studio_drafts (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL,
  draft_kind TEXT NOT NULL,                 -- 'copy'（预留 'oral' / 'replica'）
  payload JSONB NOT NULL,                   -- 整个 StudioDraft 序列化（script/ipId/sourceId/prompt/…）
  script_confirmed BOOLEAN NOT NULL DEFAULT FALSE,
  revision INTEGER NOT NULL DEFAULT 0,
  updated_at TIMESTAMPTZ NOT NULL,
  UNIQUE (user_id, draft_kind)
);

-- 我的文案：显式保存的版本列表（对应前端 savedScripts 内存数组）
studio_saved_scripts (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL,
  script_id TEXT NOT NULL,                  -- 前端 script.id，回填用
  title TEXT NOT NULL,
  text TEXT NOT NULL,
  original TEXT,
  version INTEGER NOT NULL DEFAULT 1,
  ip_id BIGINT,
  source_project_id BIGINT,
  source_kind TEXT,                         -- 'viral' | 'project' | 'link' | 'upload'
  created_at TIMESTAMPTZ NOT NULL,
  UNIQUE (user_id, script_id)
);
```

实现注：双方言兼容按仓库惯例处理（单机 SQLite 模式 JSONB 退化为 TEXT 存 JSON，参照 `025_postgres_runtime_compatibility` 思路）；PG 层 psycopg3 同步驱动，禁 ORM。

### 2.3 路由（新文件 `server/app/studio_draft_routes.py`，前缀 `/api/studio`，走现有会话鉴权）

| 方法 + 路径 | 行为 |
|---|---|
| `GET /api/studio/drafts/{kind}` | 恢复草稿；无则 404（前端按空态处理） |
| `PUT /api/studio/drafts/{kind}` | 自动保存 upsert；last-write-wins + revision 递增 |
| `DELETE /api/studio/drafts/{kind}` | 放弃草稿（确认流入下游后由前端决定是否清空） |
| `GET /api/studio/saved-scripts` | 我的文案列表（按 created_at 倒序，上限 50） |
| `POST /api/studio/saved-scripts` | 保存/覆盖一条（按 user_id+script_id 幂等） |
| `DELETE /api/studio/saved-scripts/{id}` | 删除一条 |

### 2.4 前端接线（`client/src/studio/`）

- `patchDraft` 防抖约 2s 调 `PUT /drafts/copy`（fire-and-forget，失败不打断编辑，仅角标提示）；「确认终稿」「保存版本」立即同步写。
- 挂载恢复优先级：服务端草稿 > `importProject` 带回（hash 带 projectId 时）> 空态。自存草稿恢复时保留其 `confirmed` 值（服务端为准）；`importProject` 带回维持现行"强制未确认"合同不变（`live.test.ts` 既有断言不动）。
- 「我的文案」Tab 从内存数组切换为 `GET /saved-scripts`；「保存版本」成功后 toast 去掉"云端草稿接口尚未接入"措辞。
- **终稿显式发布**：「确认终稿」且草稿含 `projectId` 时，前端额外调一次 `POST /api/projects/{id}/scripts`（版本号沿用服务端递增）——只有终稿进项目脚本版本，草稿永不污染生成门禁；两条域互相到达、语义各自干净。

### 2.5 边界

- 草稿不计费；payload 为纯业务 JSON，不得含任何密钥/token；行级按 user_id 隔离。
- 冲突处理 last-write-wins 的依据：客户版两设备单在线，同一账号并发编辑面极小；revision 字段保留为将来乐观锁升级预留。

## 3. ASR 文案提取链路（`POST /api/projects/{id}/script-from-audio`）

### 3.1 编排

沿用仓库现行"202 入队 + DB 任务 + Worker 轮询"模式（与 `script-rewrite`、`analysis-tasks` 同款），不引入 Redis/消息队列。provider 代码从 research 仓的 async httpx 改写为同步 httpx（Worker 线程内执行）。

### 3.2 管线（Worker 内执行，API 不阻塞）【已实现】

```
上传视频(已实现 uploadWorkbenchSourceVideo，assetId 入草稿 sourceAssetId)
→ 存储取原视频字节 → 本机 ffmpeg 抽音轨（-vn -ac 1 -ar 16000 -c:a aac -b:a 32k → m4a）
→ 音频传存储临时 key（tmp/asr/{project_id}/{sha256}.m4a），拿签名 GET URL
→ 按时长分流调 Fun-ASR（≤300s Flash 同步 / >300s 异步轮询）
→ 全文写任务 result_json（决策 #7，不写 scripts 表）
→ 删除临时音频（本地 tmp 文件 + COS 对象，见 3.4）
→ 前端轮询（每 2s，上限 5 分钟）→ 回填草稿 original → 跳文案工坊
```

抖音等平台直链场景（走 3.3 解析）可跳过抽取，直接把 audio/video 公网直链传给 Fun-ASR。

### 3.3 链接解析前置（Douyidou）【方案已定，实施待凭据联调】

`GET {base}/api/parse?url=…&app_id=…`，Header `Sign = md5(sorted(params).urlencode + app_secret)`；响应取 `audio[0] → video[0] → text` 降级链（`text` 非空且音视频不可用时直接作原文，跳过 ASR）。不支持视频号——视频号内容只走"上传本地文件"入口（C4 TikHub 代理负责视频号内容发现，其加密 MP4 解密+抽音频由 viral_media 管线承接）。凭据配置项 `douyidou`（app_id/app_secret）已入 REQUIRED_PROVIDER_FIELDS。

### 3.4 临时音频生命周期（决策 #6）

- 成功：拿到转写全文后立即删 COS 临时对象 + 本地临时文件，再写 scripts 版本。
- 失败：任务进入终态（FAILED/取消）同样删除；重试 = 重新抽取+上传，不保留旧音频。
- COS 侧不依赖 180 天生命周期兜底，删除为显式调用；删除失败记录告警日志并复删，不阻塞任务成功返回。

### 3.5 ffmpeg / ffprobe 分发（决策 #5）【已实现定位与接管，构建脚本就绪】

- 精简 LGPL 构建（无 x264/x265 等 GPL 库，安装包增量约 5–10 MB），NSIS 安装包内置 `ffmpeg.exe` 与 `ffprobe.exe` 到 `resources/ffmpeg/`（构建脚本 `scripts/ffmpeg-minimal/{Dockerfile,build.sh}`；二进制不入库，见该目录 `.gitignore`）。
- `start-backend.bat` 默认 `VIDEO_REPLICA_FFMPEG_DIR=%~dp0ffmpeg`；`media_tools.resolve_media_binary` 定位顺序：环境变量目录 → PATH，两者皆失败任务 fail-closed 报明确错误，不静默降级到其它解析通道。

### 3.6 计费与限额

ASR/Douyidou 为按量付费外部服务：本轮先做能力接通与联调（B 组凭据流程）；是否向客户计费、单价与配额，接入钱包前单独立项确认，不在本工作包内默认计费。

## 4. 红线核对

- 密钥零泄漏：三个凭据只进服务端密钥存储；测试夹具一律用假 key；vendor 序列化剥离与供应商名称 UI 中性化由既有红线测试锁定，新路由沿用。
- 不虚构成功：ASR/解析未配置凭据时端点返回明确"未配置"错误；前端空态与错误文案如实（禁供应商名称）。
- 迁移纪律：仅追加 `058_studio_drafts`，bump 三处 head 断言；不改冻结 revision。
- fail-closed：门禁语义（确认终稿才可下游）不因草稿持久化放松。

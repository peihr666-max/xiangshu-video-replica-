## 分阶段实施进度与待处理事项

### P1：仪表盘与经营分析统一核算读取（第一阶段已实现）

初次分析发现仪表盘使用 `operation_cost_records` 和旧外部价格推算消费收入。按用户批准，本次已改为复用 [billing_reports.statistics](../../server/app/billing_reports.py)，总览与经营分析共用逐项结算收入、有效供应商尝试成本和同一上海日期边界。充值到账仍单列；赠送积分收入为零，失败退款和重试成本按原结算事实计算。金额在读取层使用 Decimal，仅仪表盘 JSON 为兼容展示转换为数字。

缺少成本、收入来源或仍在处理时，完整成本/收入/利润返回空值；已确认部分仍单独保留。图表与卡片不会将空成本画成零。两个报告路由使用同一事务快照，避免一次读取过程中新增结算导致混用数据。

历史覆盖规则：`billing_attempt_id` 为空的旧成本、`billing_operation_id` 为空的旧 SETTLE 流水分别按发生/结算时间统计；不按某个假定切换日期截断，不把当前售价套入旧记录。已关联新版账务的兼容记录不重复计数。历史计数按日期和客户筛选；旧记录不能可靠归属当前科目/模块/提供商，因此这些筛选不会隐去历史待核对提示，相应周期的完整利润仍待核对。已确认的新版数据保持可见。此阶段没有迁移、补写或重估历史账务。

仪表盘已删除在线设备、待配对、临期激活码、设备占用的查询和返回字段；前端对应接口类型同步删除。成本待配置改查当前 `billing_tariffs`，仅覆盖配置表中的业务服务；零成本有效，售价为零或停用不自动视为错误。API 适配任务 PR #96 已核实合并，本次 `api.admin.ts` 仅修改仪表盘类型，未改变其请求/鉴权适配逻辑。

首轮后端回归 4 失败 / 3 通过、前端 2 失败 / 1 通过，确认旧实现问题；修复后相关后端 32 项、前端 4 项通过。完整门禁和本地接口核验见 [本阶段证据](LOCAL-JOINT-20260913.md#报告建议第一阶段核算读取统一)。P2、P3 仍按下述顺序推进，不能视作本阶段已完成。

### P2：客户列表与其他分页查询可减少无用工作

[admin_customer_routes.py](../../server/app/admin_customer_routes.py) 的客户列表在分页前连接设备、生成结果和钱包消费的分组聚合。当前每页 20 条，聚合却可能覆盖整个数据集。建议先按筛选取当前页客户 ID，再对这些客户聚合，CSV 导出复用相同筛选定义。需要用代表性合成 PostgreSQL 数据执行 EXPLAIN ANALYZE，才能确认收益；本轮没有生产数据基准，不能给出虚构加速比例。

[OrdersPage.tsx](../../client/src/admin/OrdersPage.tsx) 每次加载列表同时请求 `getControlReconciliation()`，可把全局汇总与当前分页分开。AccountsPage、AuditEventsPage、AdjustmentsPage 的筛选变化请求缺少统一的取消或响应序号保护；快速切换时有旧响应覆盖的可能。本轮已对 CustomersPage 修复这一问题，其他列表建议按实际响应类型逐步抽取分页查询辅助逻辑。

客户端不展示冻结积分，不意味着能删除 `reserved_credits`：预留、成功结算和失败退回仍依赖它。隐藏在线会话也不代表可以删除登录会话鉴权。

### P2：八个旧管理模块可分批退役

用 TypeScript AST 分析 `admin-main.tsx` 和 `main.tsx` 的静态/字面量动态导入，当前有 39 个管理源码模块可达，以下八个生产文件从两入口均不可达：

- `ActivationCodesPage.tsx`
- `AdminActivationSection.tsx`
- `api.economics.ts`
- `CostDetails.tsx`
- `LegacyCreditPolicyManager.tsx`
- `ProfitOverview.tsx`
- `RatesManager.tsx`
- `SessionsPage.tsx`

它们仍有测试或历史契约引用。本轮保留文件，不以“主入口不可达”直接证明所有外部工具都无依赖。建议先清理测试/导出/契约的确切消费者，再逐批删除生产文件；不要同时删除仍用于鉴权、旧订单或旧任务恢复的后端兼容实现。

两入口共享的管理目录组件仅发现 `ui/Pagination.tsx`，属于通用分页组件，不能据此认定客户构建泄漏管理员凭据。

### P2：新配置审计应显示结构化变更摘要

[admin_audit_routes.py](../../server/app/admin_audit_routes.py) 的联合查询包含通用 `audit_logs`，新费用、支付、H3 账号事件实际可读取。本轮补齐前端事件选项。旧值/新值展示主要识别旧 `operation_rate`、`customer_unit_price`，新版多字段配置事件仍可能显示空摘要。建议按事件白名单提取成本、售价、启用状态、并发值等字段；不要直接显示原始 metadata 或密钥。

### P2：商户配置的并发更新与在途订单需持续收敛

本轮为 ZPay 配置写入和默认通道写入使用同一事务锁，默认通道与输入信息一起提交，避免两步请求部分成功。已有微信待支付订单禁止更改商户身份的规则保留。配置尚未具备各管理员编辑版本校验；ZPay 商户身份更换与旧待支付订单的兼容也应补充专门约束/快照设计，不能仅凭“订单保留原 provider”保证更换商户后仍能核对旧订单。

### P3：统一样式与连接元数据来源

主 [styles.css](../../client/src/styles.css) 与 [admin-customer-detail.css](../../client/src/admin/admin-customer-detail.css) 有多轮追加的选择器覆盖，字体和列宽较难维护。本轮统一字号令牌、去除错误隐藏列规则及旧右上角身份块样式，并删除 admin-main.tsx 重复样式导入。后续按基础布局、表格、表单和详情拆分，再删除确认无调用者的选择器，避免一次性大范围删除影响客户端共享样式。

配置表默认服务地址与提供者实现的默认值可能重复，应由后端返回可公开的有效地址/默认来源；不能把“表中有默认地址”当作已配置或连通成功。`api.ts` 与 `api.admin.ts` 的管理写适配有可收敛部分，但存在其他在制任务（PR #96）的修改边界，本轮保持两文件不变。

## 不属于冗余的核心机制

H3 每账号实际额度、轮询、持久任务归属、不确定提交占位、暂停账号继续查询，分别解决不同问题；总额度叠加不能替代供应商单账号约束。支付通道切换仅影响新订单，旧订单仍按创建时的通道核对。账本预留/结算/退款、CSRF、权限、幂等记录和秘密加密都不能因界面精简而删除。

Python AST 核对当前主应用挂载的 317 个 method/path 条目，其中 86 个 `/api/control` 条目，没有发现完全相同 method/path 的重复挂载。该检查不覆盖所有参数路由歧义或安全行为，不据此宣称全仓不存在任何重复代码。

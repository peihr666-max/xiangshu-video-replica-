## 1. 一页结论

**总评**：这套系统的**业务正确性内核成熟度显著高于平均水平**——计费与任务状态同事务提交、幂等与防重放体系完整、租约 + `SUBMISSION_UNCERTAIN` 隔离不盲退款、公平队列纯 PG 行锁多实例安全、密钥体系（版本化 HMAC / AEAD / keyed digest）纪律严明。8-29《人物与首帧业务链路问题清单》中的业务缺陷绝大多数已根治，WP1-WP3 人物重构已于 8-31 上生产。

**当前的主要负债不在业务正确性，而在结构**：五条主线上的重复与巨型模块，正在让每一次业务演进付出越来越高的改动成本与回归风险：

| # | 结构债 | 规模证据 | 直接后果 |
|---|---|---|---|
| 1 | `generation.py` 上帝模块 | 6416 行（服务端 12.6%），承载 Prompt 编译 + 批次 + 任务状态机 + 公平队列 + provider + 对账 + 列表 | 任何生成相关改动都在同一文件内冲突；28 个超长函数中 7 个在此文件（09-01 快照） |

## 2. 业务流程全景

| 8. 口播稿 + AI 改写 | `POST /api/projects/{id}/script-rewrite` | `script_rewrite.py`（DeepSeek，120s） | `script_rewrite_tasks`（5min 租约） | 含 `SUBMISSION_UNCERTAIN`（已触达 provider 则人工） | **不计费**（同上） |

| 12. 归档质检 | worker 归档步 | `storage.py`（COS 媒体永久保存）+ `h3_audio_quality`（音轨检查） | 归档重试上限 5 次 | ARCHIVE_FAILED→重试/SUCCEEDED | SETTLE 要求 `cos://` 成片 |

关键横切设计：
- **版本链单表**：拆解 → 镜头卡 → 源帧 → 造型 → 首帧 → 脚本 → Prompt 全部落 `versions` 表（`next_version_number` = MAX+1，靠 `BEGIN IMMEDIATE` 串行化），血缘可追溯（WP1-WP3 已验收此点）。
- **任务表家族同构**：8 张任务表（analysis / script_rewrite / source_frame / first_frame / character_sheet / character_generation / generation / generation_reconcile）都是「PENDING→RUNNING→终态 + locked_by/locked_until/attempt + 超期回收」同一模式的手写变体。
- **worker 主循环**：单进程死循环，每轮按序扫任务表，空闲 `time.sleep(1.0)`（`generation_worker.py:1019/1044`）。

### 2.2 客户版商业化链路（V3）

| 环节 | 入口 | 核心机制 | 安全要点 |
|---|---|---|---|
| 激活码 | `POST /api/customer/activate` | 六态矩阵（GENERATED→…→REVOKED/EXPIRED 死态）；140bit 熵 Crockford 编码；DB 只存 keyed digest（版本化 HMAC 支持轮换）；`FOR UPDATE` 锁码行；单事务建 users+wallets+device+码翻 ACTIVE | 反枚举统一拒绝 + PBKDF2 固定时延；双维限流（IP 被封不烧 code 维度）；一次性 AEAD 导出（batch_id 为 AAD） |
| 设备/会话 | login/switch/heartbeat/logout | 每用户单行 `customer_session_state`（epoch 单调）；五分支状态机（续租/恢复/超时接管/显式切换/409 冲突——绝不静默踢人）；90s 租约 30s 心跳 | 设备令牌只存 keyed digest；`FOR UPDATE` 串行化全部写者 |
| 围栏/幂等 | 所有客户写路由 | `fenced_pg_transaction`：业务事务内复验五元组（user/device/session/epoch/lease）+ `clock_timestamp()` 判租约；提交证据表 | `(operation, scope, key_digest)` 唯一；响应用 AES-256-GCM 封存可重放 |
| 首充/充值 | `POST /customer/recharge-orders` → ZPay → 回调 | 下单（金额校验/定价 `CUSTOMER_STANDARD`）→ 网关 → `GET /api/payments/zpay/notify` 验签 → `confirm_recharge_payment` | MD5 为协议要求（已标注）；`hmac.compare_digest`；重复参数 400；跨单 trade_no 查重；条件 UPDATE+rowcount 幂等；int4 溢出守卫；管理端主动对账兜底 |
| 钱包计费 | 建批/worker | `internal_billing.py` 为**双轨共用内核**（名字带 internal 属历史遗留）：RESERVE 条件扣减原子；SETTLE 要求 SUCCEEDED+ARCHIVED+`cos://`；RELEASE 退款；确定性幂等键 `reserve:{task}:{round}` | 计费不变量违反抛 `BillingInvariantError` fail-loud；悬挂预留有每日对账脚本（8-29 批次 4.4） |
| 公平队列 | worker 领取（仅 PG） | `user_queue_cursors` + `FOR UPDATE SKIP LOCKED`，每用户并发 1，最久未调度者优先，空用户轮转防饿死（8 轮上限）；关闸时回退全局 FIFO（同样 SKIP LOCKED） | 锁序固定 cursor→task；多实例无争抢、无内存锁；灰度开关落 `runtime_settings` |
| 多租户隔离 | 全部项目/资产路由 | `require_project_access`/`require_asset_access` + 客户写路由统一走围栏写者 | A/B 账号交叉访问全拒（WP 清单验收项） |

### 2.3 前端与桌面壳承载

- **三入口**：`RootApp.tsx` 按 pathname 分发 `/customer*`（七屏状态机：checking/activation/login/binding-conflict/workspace/session-expired/session-replaced/device-revoked）、`/admin*`（8 子页）、其余内部版（hash 路由 `#projects/...`）。
- **内部工作区双动线**：`AnalysisWorkspace.tsx`（1626 行，三 tab：内容/人物/生成，stale 级联清下游选择）与 `ProjectDetailFlow.tsx`（650 行，五段自上而下，自动匹配人物参考）。状态源已上提到 `useGenerationDrafts`（1130 行，幂等恢复+代际守卫）与 `useWorkspaceReadiness`（纯函数就绪计算，与服务端 `PROMPT_PARAMETERS_MISMATCH` 契约对齐）。
- **全轮询、无推送**：批次进度 2s（指数退避至 16s）、健康 5s、充值 2s、心跳 30s；api 层内 while 轮询等待后台任务（统一 1.5s，超时 10–20min，同 taskId Map 去重）。无 WebSocket/SSE。

`db_portable.py` 单 SQL 源方案：业务层写 PG 规范 SQL，SQLite 道经 `translate_to_sqlite` 有界翻译（`%s→?`、剥 SKIP LOCKED、时间函数/cast 翻译，未识别语法 fail-closed）；`BusinessConnection` 统一门面。客户生产 fail-closed（拒 SQLite/强制 TLS）。迁移链 51 个文件单 head，但存在**编号与链序错位**（无 030，实链 `027→031→028→029→032`，031 docstring 自述由 030 改号而来）。

## 3. 流程健康度：亮点与风险

### 3.1 值得保持的亮点（重构时不要破坏的东西）

1. **计费-状态原子性**：RESERVE 在建批事务内、SETTLE/RELEASE 在任务终态事务内（`generation.py:1594-1792`、`finalize_generation_archive:4888-4947`、`mark_task_*:4998-5081`）——这是全系统最值钱的性质。
2. **付费调用永在事务外 + 先落库再调用**：provider task_id 拿到瞬间先落库（`task_created_observer`）；worker PG lane 每步短事务；首帧付费轮次有 checkpoint。
3. **不确定态显式隔离**：`SUBMISSION_UNCERTAIN` 不自动重试不盲退款，与「不改变真实付费提交事实」的红线一致。
4. **公平队列的 PG-first 实现**：无内存锁、无外部组件、灰度开关 + 无论开关都维护 cursor。
5. **零裸 except、错误码体系化、敏感信息只记类型不记内容、DSN 统一脱敏**。
6. **测试规模**：服务端 1261 用例（客户域密集）、前端 568 用例近 1:1 组件配套、10k 队列负载压测、Playwright 客户 E2E、三层 CI 门禁。

### 4.3 事务边界审计

**用得对**：建批（prompt CAS 消费 + 任务插入 + 逐任务 RESERVE 同一事务）；任务终态与 SETTLE/RELEASE 同事务；worker PG lane 每步短事务、付费 I/O 全在事务外；支付回调单事务幂等入账；对账用 SAVEPOINT；会话/激活码 `FOR UPDATE` 串行化。

**P1 worker 空闲退避（对应 R3；因 N3 修订，收益高于初版估计）**

**P2 complete_upload 客户道事务边界 + 内存优化（对应 R1 分道结论，2026-09-02 修订）**

**P3 SUBMISSION_UNCERTAIN 半自动对账（对应 R4，需运营决策）**
保持「不改变真实付费提交事实」红线：新增定时任务自动 `enqueue_generation_reconcile_operation`（只查 provider 真状态、SETTLE/RELEASE 仍走既有规则），人工只处理 reconcile 后仍不确定的少数。若采纳，管理端 `confirm_not_charged` 保留为最终兜底。

**P4 前端 api.ts 拆分 + 错误层统一**

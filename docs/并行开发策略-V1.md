# 并行开发策略 V1

> 版本：V1.0
> 日期：2026-09-10
> 状态：已确认，待实施
> 适用：客户版 V3 CW-001~060 收敛任务

## 1. 背景与问题

### 1.1 当前瓶颈

客户版 V3 收敛任务（CW-001~060）采用串行开发模式，每个任务的完整周期：

```
任务 X 开发 → push → CI 等待（21-30分钟）→ 合并 → 任务 X+1 开发 → ...
```

**CI 等待是真正的长杆**：
- Linux 全量 pytest：21-30 分钟
- 前端/Tauri/服务端全套门禁：`npm run check`
- 三门禁 CI：secret 扫描 / Linux 质量门 / Windows NSIS

**传统串行开发的问题**：
- CI 等待期间开发者空闲
- 任务切换成本高（新建 worktree、切换分支、重新加载上下文）
- 总时间 = Σ(任务开发时间) + Σ(CI 等待时间)

### 1.2 已有尝试的教训

**多 worktree 并行开发**（2026-09-08~09-10）：
- 同时开 5 个 worktree（cw-work/cw009/cw010/cw012/cw013）
- 结果：命名与内容不匹配、账本连环冲突、分支混乱
- 教训：AGENTS.md 硬红线"同一时间只开一个任务分支"是有原因的

**核心矛盾**：
- 账本 §18 是所有任务的唯一真源，多分支同改账本会连环冲突
- 共享文件（RootApp.tsx、api.ts、main.py）是热点，多分支同改会冲突
- 但 CI 等待时间确实可以重叠

## 2. 策略核心：重叠 CI 等待而不是合并

### 2.1 新开发周期

```
任务 X 开发 → push → CI 等待（21-30分钟）[同时做 X+1 只读调研] → 合并 → 任务 X+1 开发（已有调研基础）→ ...
```

**关键洞察**：
- CI 等待期间，任务 X 的代码已经冻结（push 后不再修改）
- 此时可以在**同一 worktree** 里做任务 X+1 的**只读调研**
- X 一合并，X+1 立刻在新分支开工，零空等

**总时间优化**：
- 传统：Σ(任务开发时间) + Σ(CI 等待时间)
- 新策略：Σ(任务开发时间) + max(CI 等待时间, 下一任务调研时间)
- 如果调研时间 < CI 等待时间，则 CI 等待被完全重叠

### 2.2 只读调研的边界

**允许的操作**（不建分支、不动账本、不改代码）：
- 读任务规格（V3 剩余任务清单、代码开发清单）
- 读相关文件（理解现有实现、识别修改点）
- 列计划（识别依赖、冲突面、测试策略）
- 写调研笔记（本地文件，不提交）

**禁止的操作**：
- 建分支（git checkout -b）
- 改账本（docs/客户版任务清单-V3.md §18）
- 改代码（任何 git add/commit）
- 改共享文件（RootApp.tsx、api.ts、main.py 等）

**原因**：
- 避免与正在 CI 的任务 X 冲突
- 避免账本连环冲突
- 保持 worktree 干净，CI 失败时可以快速修复

### 2.3 任务 X+1 开工时机

**触发条件**：任务 X 合并到 main（PR squash merge 完成）

**开工流程**：
1. `git fetch origin --prune`
2. `git checkout main && git pull`
3. `git checkout -b feat/customer-v3-cwXXX-短横线描述`
4. 基于调研笔记，立即开始开发（无需重新理解任务）

**零空等**：从任务 X 合并到任务 X+1 开工，< 1 分钟

## 3. CodeReview 子代理：push 前自检

### 3.1 使用场景

**本地 CodeReview 子代理**（Qoder IDE 内置）：
- 速度：1-2 分钟（CW-013 实测）
- 能力：抓逻辑错误、安全漏洞、代码规范问题
- 时机：push 前自检，省一个 push/CI 往返

### 3.2 与 CI 的关系

| 检查项 | CodeReview 子代理 | CI 门禁 |
|---|---|---|
| 逻辑错误 | ✓ 快速抓 | ✓ 但慢（21-30分钟） |
| 安全漏洞 | ✓ 快速抓 | ✓ 但慢 |
| 代码规范 | ✓ 快速抓 | ✓ 但慢 |
| 全量 pytest | ✗ 不跑 | ✓ 跑 |
| 前端/Tauri 构建 | ✗ 不跑 | ✓ 跑 |
| 三门禁 CI | ✗ 不跑 | ✓ 跑 |

**策略**：
- CodeReview 子代理作为"push 前自检"，抓掉明显问题
- CI 门禁作为"最终验收"，跑全量测试
- 两者互补，不替代

### 3.3 与"下一任务调研"并行

**CodeReview 子代理运行时**（1-2 分钟）：
- 可以同时做任务 X+1 的只读调研
- 两者不冲突（CodeReview 只读当前分支，调研只读规格/文件）

**流程**：
```
任务 X 开发完成 → 启动 CodeReview 子代理（1-2分钟）[同时做 X+1 只读调研] → push → CI 等待（21-30分钟）[继续 X+1 只读调研] → 合并 → X+1 开工
```

## 4. 评审问题分级

### 4.1 分级标准

| 级别 | 定义 | 处理方式 | 示例 |
|---|---|---|---|
| **M（阻塞）** | 逻辑错误、安全漏洞、数据丢失风险 | 当任务内修完再合并 | 越权访问、账务不平、fencing 失效 |
| **m（应修）** | 代码规范、测试覆盖不足、文档缺失 | 当任务内修完再合并 | 缺测试、命名不规范、注释缺失 |
| **n（可选）** | 风格偏好、优化建议、跨任务观察 | 登记为后续任务的 follow-up | 代码重构建议、性能优化、架构改进 |

### 4.2 处理流程

**M/m 级别**：
1. 评审发现问题
2. 当任务内修复
3. 重新 push
4. CI 通过后合并

**n 级别**：
1. 评审发现问题
2. 登记为后续任务的 follow-up（写入调研笔记）
3. 当前任务正常合并
4. 后续任务开发时一并处理

### 4.3 避免评审阻塞

**原则**：
- M/m 级别必须修完再合并（保证质量）
- n 级别不阻塞当前任务（保证进度）
- 跨任务观察登记为 follow-up（避免遗漏）

**示例**：
- CW-013 评审发现 `RootApp.tsx` 有性能优化空间（n 级别）
- 登记为 CW-015 的 follow-up（CW-015 也碰前端）
- CW-013 正常合并，CW-015 开发时一并优化

## 5. 与多 worktree 并行的结合

### 5.1 两种策略的关系

| 策略 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|
| **重叠 CI 等待**（本策略） | 同一车道内串行任务 | 零空等、无冲突、账本干净 | 不能跨车道并行 |
| **多 worktree 并行** | 不同车道独立任务 | 跨车道并行、总时间更短 | 账本冲突、共享文件冲突 |

### 5.2 结合方案

**车道内**：采用"重叠 CI 等待"策略
- 前端车道 A：CW-013 → CW-015 → CW-017 → CW-016 → CW-018（串行，重叠 CI 等待）
- 后端车道 C：CW-025 → CW-026 → CW-054/055/056/057 → CW-029/030/031（串行，重叠 CI 等待）
- 数据车道 E：CW-033 → CW-034/035/036/037 → CW-038/039（串行，重叠 CI 等待）

**车道间**：采用"多 worktree 并行"策略
- 前端车道 A、后端车道 C、数据车道 E 各开一个 worktree
- 三个车道完全独立，无文件冲突
- 账本集中改：每个车道只在收尾时改一次账本 §18

### 5.3 第一波并行示例

**worktree 1（前端车道 A）**：
```
CW-013 开发 → push → CI 等待[做 CW-015 只读调研] → 合并 → CW-015 开工 → ...
```

**worktree 2（后端车道 C）**：
```
CW-025 开发 → push → CI 等待[做 CW-026 只读调研] → 合并 → CW-026 开工 → ...
```

**worktree 3（数据车道 E）**：
```
CW-033 开发 → push → CI 等待[做 CW-034 只读调研] → 合并 → CW-034 开工 → ...
```

**三个 worktree 完全独立，无冲突**

## 6. 具体操作流程

### 6.1 单任务完整周期

```
1. 任务 X 开发（在当前分支）
   ↓
2. 开发完成，启动 CodeReview 子代理（1-2分钟）
   [同时做任务 X+1 只读调研]
   ↓
3. CodeReview 通过，push 到 origin
   ↓
4. CI 等待（21-30分钟）
   [继续做任务 X+1 只读调研]
   ↓
5. CI 通过，PR squash merge 到 main
   ↓
6. 任务 X+1 开工（< 1 分钟）
   - git fetch origin --prune
   - git checkout main && git pull
   - git checkout -b feat/customer-v3-cwXXX-短横线描述
   - 基于调研笔记，立即开始开发
```

### 6.2 只读调研清单

**任务 X+1 只读调研内容**：
1. 读任务规格（V3 剩余任务清单 §4.CW-XXX）
   - 类型/责任、前置任务、执行条件
   - 复用现有、剔除重复开发、仅做剩余
   - 文件/对象、增量验收、保留验收底线
   - 完工标准、必交证据

2. 读相关文件（理解现有实现）
   - 识别修改点、依赖关系、冲突面
   - 列出现有测试、识别测试缺口

3. 列计划（写入调研笔记）
   - 修改文件清单
   - 测试策略（先红后绿）
   - 依赖关系（前置任务是否已完成）
   - 冲突面（是否与正在 CI 的任务 X 有交集）
   - follow-up（n 级别评审问题）

4. 写调研笔记（本地文件，不提交）
   - `docs/research/CW-XXX-调研笔记.md`
   - 包含：任务理解、修改计划、测试策略、风险点

### 6.3 账本更新策略

**原则**：每个车道只在收尾时改一次账本 §18

**操作流程**：
1. 任务 X 合并到 main 后，立即更新账本 §18
   - 把任务 X 标记为 [x] 已合入（PR #XXX）
   - 把任务 X+1 标记为 [~] 进行中

2. 避免多分支同改账本
   - 只读调研期间不改账本
   - 任务开工后才改账本（标记为 [~] 进行中）
   - 任务合并后立即改账本（标记为 [x] 已合入）

3. 合并冲突处理
   - 如果多个车道同时改账本，手动解决冲突
   - 保留所有车道的更新（不丢失任何任务状态）

## 7. 预期收益

### 7.1 时间优化

**传统串行开发**：
- 每个任务周期：开发时间 + CI 等待时间（21-30分钟）
- 10 个任务总时间：10 × (开发时间 + 25分钟) = 10 × 开发时间 + 250分钟

**重叠 CI 等待策略**：
- 每个任务周期：开发时间 + max(CI 等待时间, 调研时间)
- 如果调研时间 < CI 等待时间，则 CI 等待被完全重叠
- 10 个任务总时间：10 × 开发时间 + 25分钟（只有最后一个任务的 CI 等待）

**节省时间**：9 × 25分钟 = 225分钟 = 3.75小时（10 个任务）

### 7.2 质量提升

**CodeReview 子代理**：
- push 前自检，抓掉明显问题
- 减少 CI 失败率，省一个 push/CI 往返（21-30分钟）

**评审问题分级**：
- M/m 级别当任务内修完，保证质量
- n 级别不阻塞当前任务，保证进度
- 跨任务观察登记为 follow-up，避免遗漏

### 7.3 冲突减少

**只读调研**：
- 不建分支、不动账本、不改代码
- 避免与正在 CI 的任务冲突
- 避免账本连环冲突

**车道内串行**：
- 同一车道内任务串行开发，重叠 CI 等待
- 避免共享文件冲突（RootApp.tsx、api.ts、main.py）

**车道间并行**：
- 不同车道完全独立，无文件冲突
- 账本集中改，每个车道只在收尾时改一次

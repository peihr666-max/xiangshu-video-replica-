## 二、技术架构

### 2.1 总体形态

**一套代码库、双运行模式的单体架构**，内部单机线（SQLite + 本地存储 + Tauri sidecar 同机后端）与客户云线（PostgreSQL/psycopg3 + 腾讯 COS + 多实例 + 可信代理边界）共存，由 `VIDEO_REPLICA_CUSTOMER_PRODUCTION` 等环境变量切换，客户生产模式下 SQLite/缺 DSN/fake provider/dev 身份等全部 fail-closed 启动失败（`bootstrap.py` 四层闸门，安全专项确认无旁路）。

### 2.2 服务端（Python 3.12 / FastAPI / Alembic / psycopg3）

- **分层**：`app/` 平铺约 100 个模块（无目录分层，靠命名约定）：36 个 `*_routes.py` 路由全部在 `main.py:324-359` 显式装配；领域层以巨型域文件为主（`generation.py` 7169 行最厚）；worker 单进程双泳道（generation 批次 + oral 口播任务同循环 claim，`generation_worker.py:303/921`）。
- **路由面**：`/api`（generation/studio/analysis/character/钱包/充值）、`/api/oral`、`/api/independent`、`/api/viral`、`/api/assets`、`/api/customer`（激活/设备/会话）、`/api/control`+`/api/control/admin`（管理控制面）等。
- **迁移线**：001–076 共 **74 个文件**（030/060 为留空槽位，文件头有说明），head=`076_studio_notification_preferences`。覆盖核心四表→存储演化→人物/生成域→供应商→钱包按秒计费（056-059/062/063）→客户安全/设备/会话（026-039/053-055）→公平队列（041）→异步化（045-049/068）→口播飞影（064/065/072/073）→C 系列（067/070/071/074/075/076）。
- **双真源纪律**：SQLite（内部）与 PG（客户）经 `db_portable.py` 方言翻译，禁 ORM/Redis/MQ 红线执行到位；PG 侧 `psycopg_pool` 连接池 + fenced 事务（`fenced_pg_transaction` 事务内重验证会话租约）。

### 2.3 前端（React 19 / TS 5.9 / Vite 8 / Biome / Vitest）

- **三 lane 手写路由**（无路由库）：内部工作台 `/`、客户七屏状态机 `/customer`（Tauri 强制）、管理后台 `/admin`、DEV 审核路由 `/review/v1.4`。
- **API 层三层结构**：`api.ts`（5338 行手写封装约 200 函数，凭据全内存态）+ `api.admin.ts`（1582 行控制面，HttpOnly cookie + CSRF + 幂等键写契约）+ `studio/live.ts`（1073 行数据编排，`loadStudioData` 一次并行拉 9 类数据、单边失败不拖垮整页）。`generated/api.ts`（约 1.6 万行，266 path）由 `npm run generate:api` 从运行中后端生成；86ed324 已再生成消除漂移。
- **studio 主界面 21 页**（`studio/state.ts:3-25`）："新壳 + 旧成熟工作区浮层复用"（LiveWorkspacePanel）架构。

### 2.4 桌面端（Tauri 2 / Rust）

能力面刻意最小化：客户凭据金库 5 命令（macOS Keychain `ThisDeviceOnly` / Windows DPAPI+熵，明文不落盘，Linux 拒绝持久化）+ 视频下载 5 命令（Win32 自绘对话框、来源校验、blob 校验）；capabilities 仅 event listen/unlisten；客户云构建 `--no-default-features` 永不本地起后端；ffmpeg 精简 LGPL 由 sidecar 后端使用、随 NSIS 分发（缺失时任务 fail-closed）。

### 2.5 架构评价

**优点**：无 ORM/双真源红线执行彻底；幂等（request_hash/幂等键/部分唯一索引）与 fencing（session epoch/租约、billing_round）纪律贯穿；注释携带评审编号可溯源；错误信息全链中文化。
**代价/风险**：`generation.py`（7169 行）、`api.ts`（5338 行）等巨型文件持续膨胀，改动局部性差、review 成本高；`app/` 平铺无分层目录，新人导航靠全文搜索；前端手写类型与生成类型的"有意放宽"点（如报价 `duration_seconds: 4|15` → `number`，调用处被迫双重断言）仍需纪律收敛。

### 4.2 本轮发现并处置

1. **修复（测试债）**：`AnalysisWorkspace.test.tsx` 「前往处理」用例缺 `waitFor(主按钮就绪)`，就绪探测异步化后点击落空（`0d91fd8`）。同文件相邻用例已有此模式。

## 五、代码质量评估

**测试规模与分布**：服务端 90 文件约 1650 个测试函数（参数化后 1908 例）——客户安全线（devices 75 / sessions 62 / admin_auth 55 / admin_activation 55）与生成计费域（generation 121）最厚；新域覆盖够用但不厚（independent 14 / analytics 6+4 / hifly 19 / viral 系列 26+ / script_from_audio 8），**无零测试新域**。前端 933 例覆盖 lane 状态机与关键流程。

**优点**：
1. 测试先行纪律真实落地（失败注入、崩溃恢复、10k 队列负载、PITR、迁移方言契约等横切重测试）；
2. 幂等三件套（request_hash + 幂等键 + 部分唯一索引）与对账兜底（悬预留、H3 对账入 worker）形成闭环；
3. 生产守卫 fail-closed 四层且互相独立；
4. 注释密度高且带 ADR/评审编号，可溯源。

**问题（按影响排序）**：
1. **P1·正确性回归（本次实测发现）**：共享容量 claim 路径并发安全被破坏（缺陷 A/B，见 §4.2/§4.4，归因 `289e768`/`58f509c`）——生产语义为并发争抢下重复 claim/超容量派发与持锁事务抛弃导致队列停摆的风险，且公平队列文件失败会级联挂死整跑（无语句级超时兜底）；

## 八、最终结论：每个业务链条都能打通吗？

- **问"代码写完了吗"**：写完了。16 条业务链 14 条前后端闭环可通；1 条（口播 retry 组合）有一个明确小断头；2 条（C5 发布、C3 链接解析）是客户决策层面的有意不接，且前端均为明示占位、无暗桩。真实页面 0 处吃假数据（唯一 mock 模块三重门控锁在 DEV 审核路由）。
- **问"链路能跑通吗"**：单机/串行语义下全部能跑通（前端 933/933、服务端 1900/1908 实测）；**并发语义下有一个真雷**——共享容量 claim 路径的两处确定性回归（§4.4）说明生产 worker 高并发争抢场景未被告住，必须先修；此外凡涉及付费 Provider/真实支付的 6 条链（真实生成、真实拆解、真实口播、真实转写、真实充值、链接解析）尚无一次真实链路验证——不是代码风险，是授权/环境风险，全部已列在账本 T35-T42 与 B 组清单中。
- **问"能交付吗"**：内部单机版线在避开并发争抢的日常使用下已具备交付条件；客户云线代码 GO 但门禁与验证双 NO-GO——先修 claim 路径回归清零门禁红灯，再以 staging 环境与人工授权完成 T35-T40，才能把证据层级从 `AUTOMATED_VERIFIED` 推进到 `PRODUCTION_GO`。
- **风险底线**：安全无 P0；计费账本本身（条件原子 UPDATE + 唯一索引 + 对账）经最厚测试仍是全库质量最高的部分；本次新增的最高风险是**调度 claim 层**（而非记账层）的并发回归——钱不会算错，但任务可能派重/派停。

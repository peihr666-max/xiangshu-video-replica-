## 2. 架构分析

### 2.1 入口与分层（健康的部分）

- 客户链 `index.html → main.tsx(21行) → RootApp(221行，7屏纯映射) → customer/* → CustomerWorkspace → StudioWorkspace`；管理链独立。两层挂载零共享，由 entryContract（12 条源码断言）双向钉死。
- **customer-state.ts + useCustomerSession 是全库最好的分层范本**：纯 reducer（每次转移带来源屏守卫、非法迁移原地返回、逐条对应规格 §4.1/§13.2）→ hook 只做副作用编排 → credential store 接口注入（Tauri/浏览器/测试三实现）。应作为其他域重构的模板。
- 构建契约体系（verify_customer_bundle：排除断言 + 阳性对照自证 + 空壳防伪绿 + symlink 拒绝 + 管理制品 CSS 包含断言）——"断言有效性本身被断言"，是 CW-019 红线可信的根基。

### 2.2 依赖矩阵与边界（结构性风险集中处）

真实依赖方向（⚠=组件级）：

```
admin-main → AdminApp → admin/* → api.ts ← api.admin.ts（仅 admin）
main → RootApp → customer/* → api.ts
                  │  ⚠→ studio/StudioWorkspace
                  └→ admin/ui/Pagination（1 处）
studio/* → api.ts + live.ts + 域内
  ⚠→ SettingsPanel、CharacterSelection、FirstFrameSelection、SourceFrameSelection（根）
  ⚠→ customer/{WalletPanel,RechargeDialog,ProfilePanel}（经 LiveWorkspacePanel）
useGenerationDrafts(根) → studio/scriptRewrite   ← 唯一反向违规的活代码
App.tsx（死壳 802 行）→ studio + 全部老组件 + styles.css（仅 3 个测试文件可达）
```

问题：① customer↔studio 双向环（CustomerWorkspace→StudioWorkspace ↔ LiveWorkspacePanel→customer/*）；② useGenerationDrafts→studio/scriptRewrite 违反"老组件不依赖新 UI 域"；③ CreationPages 直接 import 3 个根目录老选择器，未走 LiveWorkspacePanel 式集中注册。

### 2.3 状态管理架构

5 类载体并存：React state/reducer/ref、1 个 Context（StudioContextValue 17 字段）、localStorage（幂等记录/本地草稿/充值单号/批次 id，全部带 userId 前缀）、sessionStorage（scriptRewrite/viralImport 键）、**模块级可变单例**（api.ts 认证三件套 + 6 个 waiter Map + drafts/live/ProjectDetailFlow 的 frozen request 缓存——同一套模式手写了 10 遍）。

关键判断：多账号/多项目隔离**几乎全靠 key 编码约定**，唯一结构性防护是 api.ts 的 customer session owner symbol。没有任何契约钉住"新增模块级缓存必须带 scope key"——幂等 key 一旦跨账号泄漏，后果是把 A 的重试打到 B 的批次上。另：同一客户会话 token 存在三份运行时副本（credential store / useCustomerSession ref / api.ts 模块单例），一致性靠 attach/detach 调用时机约定。

### 2.4 数据流架构

API→组件共 5 条路径：① 老组件直连 api.ts 自管轮询；② studio 页面走 live.ts（1481 行领域网关，DTO 映射集中——正确的缓冲层）；③ drafts 领域 hook；④ review fixtures（dev-only）；⑤ admin lane 走 api.admin.ts。同屏双拉（StudioWorkspace 20s 轮询 vs LiveWorkspacePanel 老组件 2s 自拉）无共享缓存，一致性靠三个手工接口：closeLive 全量 refresh、onBatchCreated 上行、busyRef 双向门闩——方向正确但靠纪律，新面板忘记回调 onRefresh 无契约报错。

### 2.5 CSS / 构建架构

CSS 已形成"按使用方分桶 + 双层契约"（PR#61 拆分产物），studio 五个域 css 无全局裸规则、域隔离好。两个不可持续点：① 全局裸元素规则（:root/body/button/input）在 styles.css 与 customer-access.css 各一份双写，改全局样式要改两处；② split_customer_styles.mjs 是"一次性迁移工具被留作再生成路径"，但产物已允许手工编辑且被契约钉住——再运行脚本会无提示覆盖手工修改。建议宣布三个产物为源码、脚本改为只读 drift 校验。

## 3. 代码质量

### 3.1 客户线（评分：hook 3.5 / reducer 4 / 组件 3 / 类型 4 / 测试 4 / 一致性 2.5）

- useCustomerSession 821 行承载 9 类职责；并发内核（generation + requestId + token 三重卫兵）正确且有全库最好的竞态测试，但**防护模式三套并存**：retryLogin 用 in-flight ref、logout 用 ref+generation、switchSession 两者皆无（唯一"踢设备"写操作反而防护最弱，仅靠对话框局部 isProcessing）。
- activate 幂等键清除时机有竞态窗口（成功后即清，但后续 saveActivation 仍可能抛——注释承诺"保留到 final outcome"实现未兑现）；logout 与 401 事件交错时返回的 credentialCleared 与事实相反。
- CustomerProfilePanel 514 行/18 props、CustomerWalletPanel 797 行/20 state 是客户域的两个过载组件；CustomerWorkspace 五个 handler 重复"load token→401→onSessionExpired"骨架，且 `loadDevices/handleUnbind` 的 store 调用**无 try/catch**（vault 抛错 = unhandled rejection 无反馈）。
- **错误文案管道有 5 条**（customerVisibleErrorMessage / activationErrorText / 两个同名不同实现 errorMessage / Dialog 的 visibleError），同一网络错误在不同屏呈现不同。
- 类型安全亮点：CustomerApiError 判别建模（18 种 kind、readonly、不可伪造）；扣分点：PairingFlow 的 `data: unknown` 回退抹掉已验证类型、三处不变量靠注释不靠编译器。
- 死代码：SessionDisplacedNotice（英文、无引用）带 4 条测试在维护。

### 3.2 studio 线（架构方向清醒，债务是"堆积"）

- CreationPages 3330 行 = 5 个页面 + 4 个仅 VideoPage 使用的子组件堆放；拆分边界已勘定（CopyPage 163-760 / ReplicaPage 838-1761 / ReplacementPage 1762-2166 / VideoPage 2471-2944 / OralPage 2945-3330），**纯搬运零风险**。ReplicaPage 单组件 34 hooks（13 个 ref 手工代际校验）。
- StudioWorkspace 主函数 87 个 hook；hash 路由未知值静默回退 workbench 无诊断；新增一页要改 4 处（types/pageTitles/navGroups/switch）——换 Record 路由表可减为 2 处。
- **发现 1 个死 UI 缺陷**：CopyPage 消费 context 的 `draftSaveStatus`（CreationPages.tsx:177,632-636），但 StudioWorkspace 组装 context 时从未提供该字段（types.ts:302 声明为可选，TS 放行）→ **文案工坊的"保存状态"UI 永远不渲染**。另有 publishAccounts/selectedShotId 两个死字段、export-for-test 两个死导出。
- **报价机三胞胎**：口播/视频/复刻三套 `status+error+revision+quote` 同构状态机 + 两份逐字重复的 quoteMatchesInput + 两份时长/条数归一化——应抽 `useQuoteMachine`（计费正确性关键路径单点维护）。
- 轮询 4 层互不感知：全局 20s（有 hidden 门控）、文案提取 2s×150（无）、PeoplePages 6s×50（无）、live.ts 提取 2s（无）——后台标签页只有一处暂停。
- context value 未 memo：顶栏搜索每敲一字，21 页面 + Picker 全量重渲染。

### 3.3 API/数据层（2.5-4 分不等）

- api.ts 5788 行实际是"七大业务域 × 一套传输核心"，分层清楚但完全未分文件；225 个导出平铺使三条通道对任意组件可见。拆分切面就是现成的四条分节注释线，纯移动。
- **三条通道拷贝漂移**：requestControl 丢弃调用方 AbortSignal（隐性 bug 源）；requestApi 桥接 signal、requestCustomer 不支持；4 处超时/Content-Type/AbortError 处理逐字重复（加 api.admin.ts 是第四份）。
- **写契约语义分歧（正确性问题）**：api.admin.ts 的幂等键有明确策略"首次铸造、重试复用、终态换新"（且页面确实这样用），而 api.ts 的 controlWriteInit **每次调用无条件新造键**——同批 /api/control 写端点两条代码路径两种语义，内部通道资金类写操作的超时重放保护形同虚设。
- **脱敏双层覆盖存在旁路**：`task.error_message`/`analysis_error_message` 等 200 响应体字段在 FirstFrameSelection/CharacterLibrary/ProjectsPage 等 8+ 处直接渲染，永不过 BRANDED_SERVICE_ERRORS；且脱敏表缺 hifly/tikhub/dashscope/douyidou 四个 ProviderName（上游报错会原文透出）。另有 6 份本地 errorMessage 拷贝绕过统一入口。
- **类型双轨**：customer/wallet 模块纪律严明（生成类型别名 + drift guard 测试）；老代码 Project/ViralVideoItem 是无纪律的手写拷贝（generated 里明明有同端点类型）；api.admin.ts 15+ 张手写 interface 无任何 drift guard——管理端字段改名要等运行时才炸。
- 健壮性：超时/Abort 覆盖约 100%（加分）；**成功路径裸 `response.json()` 共 10 处**——非 JSON 的 200 响应会把英文 SyntaxError 直接抛给 UI。
- **requestId 空挂**：RequestError.requestId 字段声明了但所有通道都不写入（即用即弃）——审计对账链在客户端断了一环。

### 3.4 测试（总量厚实，风格两派）

81 文件/1247 用例，测试:源码 ≈ 1.1:1。亮点：useCustomerSession 竞态测试（late-logout 手工 gate promise 控制交错）是范本；describe 按需求号组织可回溯。两派 mock 策略并存（手写假 context vs vi.hoisted 全 API mock），假 context 使"测试绿 ≠ 集成通"。关键缺口：activate 幂等键跨失败重试断言、customer-state (state×event) 穷举表（~96 格子一个双层循环就能钉死）、logout×401 交错。

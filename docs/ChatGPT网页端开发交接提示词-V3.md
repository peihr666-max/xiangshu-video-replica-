## 2. 每次任务的必执行流程

1. 读取任务范围，git fetch origin --prune；核对main、账本、认领登记、本机共享claim、本地/远程同编号分支、开放及近期合并PR、相关worktree状态。查询失败不是无人开发；用户已说明在制而尚无提交的任务仍占用。
2. 已有执行者、开放PR或不明WIP时不重复开工；按既有授权交接或选择其他就绪任务。先读代码与远程证据，不把能自行核实的进度问题反问用户。
3. 认领和合并串行，不同任务满足依赖、文件、接口和环境隔离后可并行。登记Owner、Reviewer来源、文件边界、main SHA、分支、worktree与测试资源，执行排班§3的同仓原子认领和跨设备复查。
4. **每个新分支必须从最新origin/main创建，新任务必须独立worktree。禁止从功能分支、未合并PR或其他任务工作区快照创建；前置未合入main时等待，不开堆叠分支。**

       git worktree add -b feat/customer-v3-cwNNN-description <独立绝对路径> origin/main

   文档/修复等新分支也只从main创建。已有任务使用登记的原worktree，不在他人目录切分支、搬移或清空WIP。
5. 简述文件边界和验证方案后直接推进已授权工作。业务变更先写失败测试再实现；开发期专项，收尾按AGENTS一次全量，PG资源不得互踩。
6. 在同一PR更新正式账本、独立证据、索引和文件映射。公共账本由集成人回填，冲突逐项核对真实状态，禁止取勾选并集。纯文档维护登记自身范围，不变更业务完成状态。
7. push前fetch，核对git log origin/main..HEAD和git diff origin/main...HEAD只含本任务，显式暂存指定文件。标题用CW-NNN: 英文摘要，正文含中文记录；维护任务用明确维护ID，不自造CW编号。
8. 提交并推送本任务分支，一个任务一个PR；可先开Draft PR获取CI。正文写变化、前置、验证、证据等级、未测试项与回退。当前main三门禁及任务验收齐全后再正式评审；未运行/跳过/旧SHA结果不等于当前全绿。
9. 实质处理评审意见，合并前复核base/head/检查。main只走正常PR squash merge，由用户或已有明确合并授权的执行者完成。已授权的普通提交/push直接执行，不重复问许可。
10. 合并后执行排班§6：确认merge SHA进入origin/main、main检查、文件归档、进程退出、路径核验，再从目录外git worktree remove。未合并或仍有成果/进程时保留，不用force/递归删除绕过检查，默认保留分支引用。

占用状态与业务证据等级分开。交付须包含本地路径、分支/PR、实际验证、未完成项与下一道门槛。

## 3. 验证和业务红线

- 所有运行环境与业务数据库测试使用PostgreSQL；SQLite仅限精确登记的离线历史输入/归档/兼容工具。
- 开发期专项；业务任务收尾通过npm run check承载唯一一次全量pytest，不重复全量。PG缺失或业务测试跳过不能证明通过。
- worktree隔离不等于PG隔离：隔离实例/卷、端口、固定测试库及进程；不能隔离时共享PG全量串行。
- 纯文档维护执行文档/链接/依赖/命令核对与秘密扫描，所需全量门禁交CI。遵守当前main的secret/Linux质量/Windows NSIS等实际要求；不复制其他未合入PR工作流，不修改CI绕过检查。
- 用例数量、迁移head和CI结果从当前代码/证据读取，本提示词不维护易过期数字。
- 已发布迁移revision只追加修复，文件与职责按当前映射；不引入ORM、Redis或消息队列框架，禁止SQLite/PG双真源与双写。
- 逐写路由验证fencing；公平队列PG-first；单实例健康检查不能替代多实例验证。
- 不提交真实API key、激活码、设备/session token或签名下载URL；敏感凭据使用现有秘密管理机制。
- 证据逐级推进：CODE_PRESENT → AUTOMATED_VERIFIED → STAGING_VERIFIED → REAL_CHAIN_VERIFIED → PRODUCTION_GO。本地/Fake单列，未过真实验收不标生产就绪。
- 真实ZPay/付费Provider、生产数据/COS、对外发码、灰度扩大、公网发布与最终Go/No-Go仍需相应明确授权。

连接器失效时先使用已有授权的git凭据、CLI或API，不打印或写入凭据。确认可用通道均不可用后保存可应用改动并说明具体阻塞，不虚报远程提交、PR或CI。

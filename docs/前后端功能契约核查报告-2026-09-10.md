# 前后端功能契约核查报告（按业务模块合并）

> 版本：V2（2026-09-10）
> V2 修订：本轮实际执行了「重跑 `generate:api` + biome/tsc 验证」与「`first-frames/generate` 前端触发路径追查」，据此更正 V1 两处判断——
> ① 契约漂移实为 **1 处真漂移**（settings reveal，已修复并通过 biome+tsc）+ **1 处假阳性**（viral `POST /import-tasks` 是 `include_in_schema=False` 兼容别名，本就不进契约）；
> ② `first-frames/generate` 前端**并非遗漏**，而是走 `first-frame-tasks` 异步任务链（假阴性）。详见 §4.2、§5.1、§5.3。
> 配套文档：`docs/客户视角主界面业务模块完成度分析-2026-09-10.md`（客户视角完成度）
> 本报告回答两个问题：
> 1. **后端是否实现了前端的所有功能？**（前端调用的每个接口，后端是否有对应实现）
> 2. **前端页面显示的内容，后端是否完善了后端代码？**（前端展示的字段/数据，后端是否真的提供）
> 方法：三方端点比对 + 字段契约机制核查，逐业务模块把"前端功能 ↔ 后端实现"合并对照。

## 一、核查方法

对三个端点集合做规范化比对（路径参数统一为 `{}`、去 query、去尾斜杠）：

| 集合 | 来源 | 规模 |
|---|---|---|
| **后端实现** | `server/app/*_routes.py` 的 `APIRouter(prefix)` + `@router.<method>`，及 `main.py` 的 `@app.<method>` | 267 个 @router + 4 个 @app，规范化去重后 **236** |
| **OpenAPI 生成契约** | `client/src/generated/api.ts`（`openapi-typescript` 从后端 `/openapi.json` 生成，17508 行） | **230** paths |
| **前端调用** | `client/src/api.ts`（5740 行）+ `client/src/api.admin.ts`（1648 行），前端 API 调用 100% 集中于此两文件 | **198** 端点 |

字段级契约另有一道自动门禁：前端业务类型大量派生自 `generated/api.ts` 的 `components["schemas"]`（如 `WalletSnapshot = components["schemas"]["WalletResponse"]`，`api.ts:72-91`），并由 `client/package.json:8` 的 `check`（`tsc -b`）作为 **schema-drift gate**——后端改 schema、前端重生成契约后若字段不匹配，`tsc` 直接报错。

## 二、总体结论（先给答案）

### 问题 1：后端是否实现了前端的所有功能？——**是，未发现真缺口**

- 前端调用 198 个端点，**191 个后端直接实现**；
- 剩余 7 个（比对脚本 A 类）**全部是规范化假阳性**，后端均有对应实现：
  - `${suffix}`/`${query}` 直接拼在路径尾（未带 `?`）：`customers.csv`、`simple-characters/library`、`studio/materials`、`viral/favorites`、`generation-batches`——后端都有同名端点；
  - 动态变量拼接后端的具体枚举端点：`/api/oral/tasks/{}/${action}` ↔ 后端 `archive-retry`/`cancel`/`refresh`/`billing-reconcile`；`/api/person-identities/{}/{}-upload-intent` ↔ 后端 `authorization-upload-intent`/`source-upload-intent`。
- **结论：不存在"前端调用了、后端没实现"的功能缺口。前端 API 层与后端路由高度对齐。**

### 问题 2：前端显示字段后端是否完善？——**有制度保证 + 高覆盖，1 处真漂移（本轮已修复）**

- 前端调用端点 **190/198 落在 OpenAPI 生成契约内**，其响应字段由 `generated/api.ts` + `tsc` 门禁与后端 schema 强制一致——**前端无法凭空显示后端 schema 里不存在的字段**；
- 比对脚本 B 类（契约有、后端无）= **0**，无僵尸契约；
- **发现 1 处真契约漂移（D 类）**：settings reveal 端点后端已实现、`generated/api.ts` 未收录——**本轮已重跑 `generate:api` 修复**（+52 行，biome/tsc 全绿）。另 1 处（viral `POST /import-tasks`）经核查是 `include_in_schema=False` 的兼容别名，属**假阳性**，本就不进契约（详见 §5.1）。

### 契约健康度评级

| 维度 | 评级 | 依据 |
|---|---|---|
| 端点覆盖（前端功能后端是否实现） | **优** | 198 前端调用 0 真缺口 |
| 字段契约（前端显示后端是否完善） | **良** | 190/198 受 codegen+tsc 门禁保护；1 处真漂移已修复 + 手写类型区待收敛 |
| 契约新鲜度（generated 是否跟随后端） | **已同步** | 本轮重跑 generate:api，reveal 端点已纳入（+52 行，biome/tsc 全绿） |
| 反向覆盖（后端能力前端是否接全） | **良** | 少数后端端点前端有意未接或待确认（第五章） |

## 五、发现的真问题（分类与处置建议）

### 5.1 契约漂移核查结果（本轮已重跑 codegen 修复）

V1 报了 2 处漂移，本轮实际重跑 `generate:api` + 追查后更正为 **1 真 1 假**：

| 端点 | V1 判断 | 核查真相 | 处置结果 |
|---|---|---|---|
| `/api/admin/settings/providers/{}/secrets/{}/reveal` | 真漂移 | ✅ **确是真漂移**（后端 openapi 有、generated 缺） | **已修复**：重跑 generate:api 纳入（+52 行，含 paths+operations 定义），biome/tsc 全绿 |
| `POST /api/viral/import-tasks` | 真漂移 | ❌ **假阳性**：`viral_import_routes.py:424-434` 同函数双路由，`/import-tasks` 标 `include_in_schema=False`（兼容别名），公开端点 `/videos/import-tasks` 已在契约 | 无需处置（本就不进 OpenAPI） |

- 根因：`generated/api.ts` 是某时间点从后端 `/openapi.json` 生成的快照，settings reveal 端点新增后未重新生成。
- **本轮验证**：`git diff` 收敛为 **+52 行 / -0 删除**（0 删除=后端 openapi 纯增量演进，前端零破坏）；`biome check` EXIT=0、`tsc -b` EXIT=0。
- **发现一个工具链陷阱**：`openapi-typescript` 原生输出 **4 空格缩进**，但 `biome.json` 要求 **2 空格**且未排除 `generated/`，单跑 `generate:api` 会 `biome check` EXIT=1（卡 CI Linux 质量门）。既有流程实为"generate:api 后再 biome format"。**建议**：把 `generate:api && biome check --write src/generated/api.ts` 固化为一个脚本，或把 `generated/` 加入 biome ignore，并纳入任务收尾门禁。

### 5.2 前端手写类型区（不受 codegen+tsc 保护）——潜在漂移

- `api.ts` 中 `CurrentUser`（:61-66）、`ControlAccount`（:93-102）、`ControlRechargeOrder`（:111-117）等为**手写类型**，未派生自 `generated/api.ts`。这些字段与后端 schema 无 tsc 自动校验，是字段漂移的潜在区。
- 现状：多为稳定的身份/账户字段，风险可控。**建议逐步迁移为 generated 派生**（项目已对钱包/充值类型这么做，见 `api.ts:68-91` 注释）。

## 六、结论

1. **后端完整实现了前端调用的所有功能。** 前端 198 个调用端点，后端 100% 有对应实现（191 直接对齐 + 7 规范化假阳性），**无"前端调了后端没有"的功能缺口**。前端 API 调用高度集中在 `api.ts`/`api.admin.ts` 两文件，与后端 38 个 router 的 267 个端点结构清晰对应。

2. **前端显示字段由 OpenAPI codegen + tsc 门禁保证与后端一致，覆盖率 190/198。** 项目用 `generated/api.ts`（17508 行自动生成契约）把后端 schema 变成前端类型，`tsc -b` 作为 schema-drift gate——**前端页面显示的字段，后端 schema 必然已定义**，否则前端类型检查不通过。这是"前端显示后端是否完善"最有力的制度性答案。

3. **契约漂移本轮已收口**：① 唯一真漂移（settings 密钥 reveal）**已重跑 `generate:api` 修复**（+52 行，biome/tsc 全绿）；V1 报的另一处（viral 导入 POST）经核查是 `include_in_schema=False` 兼容别名，属假阳性。**遗留改进**：把 generate:api + biome format 固化进任务收尾门禁，并逐步把前端**手写类型**（CurrentUser/ControlAccount）迁移为 generated 派生。

4. **反向看，后端能力略超前端接入**：`character-versions/{}/archive` 等少数端点后端已备、前端未接（有意的架构选择）。**`first-frames/generate` 本轮已确认非遗漏**——前端走 `first-frame-tasks` 异步任务链（幂等+轮询+断点续接），比同步端点更健壮；该同步端点是并存的兼容路径。

5. **与客户视角完成度的关系**：本报告证明**前后端接口契约层是健康的**（对齐度高、有自动门禁）。配套文档中客户感知的缺口（钱包 F1、发布暂缓、视频生成"敬请期待"、数据看板真实回流）**均不是"后端没实现前端功能"或"前端显示后端没数据"的契约缺口**，而是分别属于：前端组件接线错误（F1）、产品功能暂缓（发布）、后端能力开关未开（Provider 验收）、真实数据源未接（发布链路）。**换言之，前后端"接口对齐"已完成，卡点在"真实链路开闸"与"个别前端接线修复"，而非契约缺失。**

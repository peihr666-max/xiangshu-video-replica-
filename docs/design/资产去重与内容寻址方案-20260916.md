## 三、设计原则

1. **内容寻址（CAS）做物理层**：对象的物理键由内容哈希决定，同一份内容全局只存一份。
2. **引用计数做安全层**：对象能否删除，只看引用计数，**不再做 `storage_uri` 字符串比较**。
3. **授权隔离做逻辑层**：物理共享不等于逻辑可见。`assets` 表仍是"用户的资产视图"，权限检查保持在 asset 层。
4. **分层去重键**：能用业务唯一键的（爆款、派生物）就不硬算哈希；只有用户任意上传的才用 sha256。
5. **禁止跨用户共享的清单要显式写死**：含人脸的素材一律不跨用户。

### 3.1 补充：闸门的失败姿态（实施中确立）

收敛删除时发现的原则，**后续所有改动都必须遵守**：

- **拒绝删除** = 泄漏 1 个对象（回收器兜底，最小代价）；
- **错误放行** = 删掉他人共享字节，**不可回滚**。

因此闸门一律**宁可少删**。这条直接决定了 §七 的闸门设计。

## 四、目标架构


### 4.1 新增内容登记表（去重的唯一权威索引）

```sql
CREATE TABLE content_objects (
  id            text PRIMARY KEY,
  sha256        text        NOT NULL,
  size_bytes    bigint      NOT NULL CHECK (size_bytes > 0),
  content_type  text,
  provider      text        NOT NULL,
  bucket        text        NOT NULL,
  object_key    text        NOT NULL,
  scope         text        NOT NULL CHECK (scope IN ('user','global')),
  ref_count     integer     NOT NULL DEFAULT 0 CHECK (ref_count >= 0),
  reclaim_after timestamptz,
  verified_at   timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (sha256, size_bytes, provider, bucket, scope)
);
CREATE INDEX idx_content_objects_reclaim ON content_objects (reclaim_after)
  WHERE ref_count = 0 AND reclaim_after IS NOT NULL;
```

`scope` 的引入是关键：**同一个 sha256 在 `user` 域和 `global` 域各自独立**，从表结构上杜绝"人脸照片被跨用户命中"。

**实施与初稿的两处差异（都是必需的）**：

1. **`scope_owner` 列**：`user` 域必须带属主，否则两个用户的同哈希内容会互相命中。  
   实际建表还带 `pinned` 布尔列——`pinned=True` 的对象（如爆款共享缓存）**永不回收**，  
   因为它的所有权不在 asset 图内。
2. **唯一约束用两条 partial unique index 实现**，不是单条 UNIQUE：
   - `uq_content_objects_user (sha256, size_bytes, provider, bucket, scope_owner) WHERE scope='user'`
   - `uq_content_objects_global (sha256, size_bytes, provider, bucket) WHERE scope='global'`  
     原因：PostgreSQL 的唯一索引把 **NULL 视为互不相同**，单条 UNIQUE 无法同时服务  
     "user 域按属主唯一"和"global 域全局唯一"两种语义。

### 4.2 CAS 对象键布局

```
content/{sha256[0:2]}/{sha256[2:4]}/{sha256}.{ext}
```

两级分片，避免单目录对象数爆炸。实现见 `content_store.content_object_key()`。

### 4.3 assets 表变更

```sql
ALTER TABLE assets ADD COLUMN content_object_id text REFERENCES content_objects(id);
CREATE INDEX idx_assets_sha256 ON assets (sha256, size_bytes);
CREATE INDEX idx_assets_content_object ON assets (content_object_id);
```

- `assets.storage_uri` **保留不动**（兼容存量、便于回滚），但新逻辑一律经 `content_object_id` 解析。
- `idx_assets_sha256` 顺带解决当前去重查询走 `owner → projects → assets` 的低效问题。
- 实际迁移还加了 `idx_assets_storage_uri`：闸门需要在删除前按 `storage_uri` 反查存活引用。

### 5.1 ⛔ 安全红线（必须写死并在测试中固化）

- **A3 / A4 / A5 人物类素材严禁跨用户共享**，即使哈希完全相同（同一张脸、同一份授权书）。原因：这些是客户私密资料，跨用户命中会直接泄露他人人脸与证件。
- 参考视频**也不建议**升为 global：可能是客户自有的商业素材。
- 唯一允许 global 的是爆款库（内容本身来自公开平台）。
- **已固化**：`scope` + `scope_owner` 表结构保障；`test_dedup_cas_pg.py` 有 user 域隔离用例，  
  并有一条**跨用户素材复用必须不命中**的用例（见 §五之二）。  
  A3/A4/A5 接入后**再补一条人物类的跨用户红线用例**：同一份授权书字节换用户上传，必须不命中（见 §5.5）。  
  人物链路的属主不是操作者，而是 `identity.owner_user_id`（见 §5.5 第 2 点）。

### 5.3 C1/C2 为什么暂缓（不是遗漏）

落库处去重只省**存储**；真正省**算力**要在**生成前**按  
`(source_sha256, 抽取参数 / appearance_fingerprint)` 拦截。

改动风险高于设计 P3 的收益。建议单独开任务，先定"复用帧是否计费"再动代码。

### 5.5 A3/A4/A5 人物素材去重的实现（本轮新增 · **只省存储，省不掉传输**）

**先说结论，避免误解**：这三条链路做不到 A2 那种"体感秒传"。

A2 在 `upload-intent` 阶段就命中，`upload_required=False`，浏览器一个字节都不用传。而 A3/A4/A5 的**完成路径必须读到真实字节**：

- **A3 授权文件**：要过 `validate_authorization_content()`（PDF / 图片内容校验）；
- **A4 原始照片**：要过源图审查（inspection），失败会走 `persist_source_inspection_failure`；
- **A5 简单人物**：要读字节算 sha256 并落成 `character_source_image` 资产。

命中登记表也**不能跳过这些校验**——不读字节就无法确认"这次上传的内容确实是授权书 / 确实是一张合规的人脸照"。  
所以客户端**仍然要传一次**；收益是**服务端不再写第二份 verified 副本**，新资产直接指向已存在的对象（省存储、省对象数，不省带宽）。

**实现要点**：

1. **先查重，再写（顺序不能反）**：`verified-uploads/{asset_id}/{digest}/{filename}` 的键**嵌入了 asset_id**，  
   而 asset_id 每次上传都不同 → 必须先算出本次的 key 再决定是否写。  
   为此从 `storage.store_verified_upload` 中抽出 `verified_upload_object_key()`，  
   让去重逻辑能在写之前算出**同一个** key，避免两处格式串漂移。
2. **属主取 `owner_user_id`**：新增 `_identity_owner_user_id()`，取  
   `identity["owner_user_id"] or identity["created_by"] or actor.id`。  
   人物资料是客户私密资料，属主必须是**资料归属人**，而不是"当前谁在操作"。
3. **A4 的失败路径也要登记**：`persist_source_inspection_failure(..., content_object_id=...)`，  
   否则审查失败的孤儿对象没有引用计数保护，会被提前回收。
4. **`content_object_id` 一律做成可选形参**：`update_completed_asset()` /  
   `persist_source_inspection_failure()` 都在有该列时走 UPDATE、没有时走原 UPDATE，  
   未接入登记表的老调用方行为完全不变。
5. **A5 的孤儿对象不即时删除**：`simple_character.py` 命中已有对象后，本次写下的字节成为孤儿，  
   留给 `upload_cleanup` 走闸门回收——刻意不在提交前删（见 §3.1：宁可泄漏 1 个可回收对象）。
6. **两个完成路径共用一个助手** `_retain_identity_content()`，保证 A3 / A4 的  
   "命中返回已有 uri / 未命中才写" 语义完全一致。

**测试固化**（`test_dedup_cas_pg.py`）：

- `test_authorization_upload_reuses_bytes_within_one_owner`——同一属主两次上传同一份授权书，  
  `verified-uploads/` 下只应有 **1 个**对象键；第二次资产的  
  `metadata["content_deduplicated"] = True` 且指向同一个 `content_object_id`。  
  ⚠️ 断言只数 verified 键：**pending 对象仍是 2 个**（客户端真的传了两次），去重只发生在 verified 落库处。
- `test_authorization_upload_never_reuses_another_owners_bytes`——换一个用户上传**完全相同**的字节，  
  必须**不命中**，各自独立占存储（这是 §5.1 红线的可执行证明）。

> 顺带修正一处旧断言：`test_cw058_content_asset_pg_matrix.py` 原先要求  
> `verified-uploads/{asset_id}/` 出现在 `storage_uri` 里。人物源图与素材库内容相同时去重会命中  
> **素材库那份**已验证副本，uri 里的 asset_id 自然不再是本次的。该用例真正要守的是  
> **"源文件被覆盖后资产仍能读到正确字节"**（防篡改），不是路径里必须有 asset_id，  
> 故放宽为 `/verified-uploads/`，字节与 sha256 断言原样保留。

### 7.2 已修复的真实缺陷（条件性，去重落地后会变成可达）

```sql
SELECT 1 FROM assets WHERE storage_uri = %s AND project_id <> %s LIMIT 1
```

当某条 assets 行的 `project_id IS NULL`（素材库、人物资料这类**用户级资产**）时，  
`NULL <> 'p1'` 求值为 **NULL 而非 TRUE** → 该行不返回 → 判定为"无共享引用" → **对象被删除，另一处引用直接失效**。

- **修复前是否可达**：不可达（对象键按 asset_id 逐次唯一）。
- **A2 接入后**：**立刻变为可达**（素材库正是 `project_id IS NULL` 的资产）。
- ✅ **已修复**：改用 NULL 安全的 `object_referenced_by_another_asset()`（以 `id NOT IN` 表达），  
  并配对照组测试 `test_legacy_null_comparison_would_have_missed_the_null_reference`  
  ——直接证明旧写法会漏判。

### 7.4 两阶段回收（已实现并通电）

1. **标记**：asset 删除 → `ref_count - 1`；归 0 时置 `reclaim_after = now() + 24h`
2. **回收**：扫 `reclaim_after <= now() AND ref_count = 0` → **`FOR UPDATE SKIP LOCKED` 锁内重读 `ref_count`**（防回收期间又被引用）→ 删对象 → 删登记行
3. 后端不可用则保留登记行，下轮重试；失败计入审计，不阻塞
4. `pinned=True` 的对象**永不回收**

| 阶段          | 内容                                                                                                                     | 是否改行为   | 状态                                    |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------- |
| **0 只加不改**  | 建 `content_objects`；`assets` 加 `content_object_id`（可空）；加索引                                                             | 否       | ✅                                     |
| **1 回填**    | 扫存量 assets，按 `(sha256, size_bytes, provider, bucket)` 分组建登记行，回填 `content_object_id`，算 `ref_count`。**存量对象键保留原位，不做物理搬迁** | 否       | ✅                                     |
| **2 修闸门**   | 收敛 17 处删除点 + 修 `rbac_routes` NULL 缺陷                                                                                   | 是（删除路径） | ✅                                     |
| **3 逐链路接入** | 顺序 A2 → B2 → C1/C2 → A3/A4/A5，每条链路独立开关，可单条回滚                                                                           | 是（新的去重） | 🟡 A2 / B2 / A3 / A4 / A5 完成，C1/C2 未做 |

**为什么不物理搬迁存量**：全量 copy 一次的对象量级不可控，且失败回滚成本极高；懒迁移能用自然流量摊平风险。

### 8.1 回填：A2 的实际前提

`content_objects` 对存量资产本来是空的 → **改造前上传过的老素材去重不命中**。  
所以回填不是"可选优化"，而是 A2 生效的前提。

- 可重复执行：已回填的资产会被跳过，反复跑会逐步收敛到查不到活干。
- **已各占一份的历史重复对象不会被自动合并**，它们会留到引用自然消失、被回收器带走为止。
- 只建登记行 + 回写 `content_object_id`，**不碰任何字节**。

### 8.2 运维命令

```bash
# 1) 回填存量（默认只读预览，确认数量后再写库）
python -m scripts.backfill_content_objects             # 预览
python -m scripts.backfill_content_objects --apply     # 写库
python -m scripts.backfill_content_objects --apply --limit 2000

# 2) 回收
python -m app.upload_cleanup --reclaim-content
python -m app.upload_cleanup --reclaim-content --reclaim-limit 500

# 3) worker 内已内置每 1 小时节流回收，无需额外配置
```

> ⚠️ **运维陷阱：`--reclaim-content` 不受 `--apply` 保护，它会直接删除字节。**  
> CLI 帮助里"默认只读预览"的说法只适用于**上传清理扫描**路径；`--apply` 也只作用于该路径。  
> 回收分支（`upload_cleanup.reclaim_content_objects`）没有 `apply` 参数，调用即真删。
>
> 它的安全性**不来自预览，而来自两阶段回收本身**：  
> ① 只有 `ref_count = 0` **且** 24h 宽限期已过的行才会入选；  
> ② sweeper 在 `FOR UPDATE SKIP LOCKED` 锁内**重读计数**后才动字节；  
> ③ `pinned=True` 的对象永不入选。
>
> 因此首次执行建议先用小批量（`--reclaim-limit`，取值 1-1000，默认 100）观察审计输出。

**建议上线顺序**：先跑回填预览核对数量 → `--apply` → 观察一段时间 → 再开 A2。  
（A2 未回填时也能工作，只是命中率低。）

## 一、总体结论（TL;DR）

**这套后端的"引擎"是高质量的，但"商业闭环的外壳"有确定性漏洞。**

- **资金安全内核（账本、幂等、并发扣减、支付回调校验、会话围栏、激活码防爆破）经过多轮评审打磨，工程化程度显著高于同类项目**——多实例抢占、公平队列、崩溃恢复、防双花均达到了可上生产的水准。
- 但排查确认了 **5 个 P0 级问题**：一半的 AI 能力（图片类/ASR/爆款分析）**完全不扣费**、**报价与实扣口径相差约 80 倍**、**支付掉单无自动补偿且用户无自助出路**、**付费成片从不落自有 COS 存储（供应商 URL 过期即永久丢失）且质检从未执行**、**商用合规前提（协议/隐私/注销）缺失**。
- P1 层的共同根因是：**异常路径的资金回收与订单补偿全部押在人工操作上，没有任何自动化兜底**（sweep/定时任务缺位）。
- 综合判断：**具备小范围内测/灰度条件，尚不具备对公网付费客户开放的就绪度**。补齐 P0 后可达可商用基线。

## 二、P0 问题清单（必须先修，共 6 项）

### P0-1 图片类与 ASR 任务完全不扣费——付费客户可无限免费使用（确定性毛损）
- **证据**：只有视频生成（`app/internal_billing.py:134-783` RESERVE→SETTLE/RELEASE）和口播（`app/internal_billing.py:264-457`，固定 1 credit）接钱包。首帧生成 `app/first_frame_routes.py:247-325`、五视图/场景图 `app/simple_character_routes.py:617-700,792`、ASR 转写 `app/script_from_audio_routes.py:24-75`、爆款分析 `app/analysis.py`、爆款导入 `app/viral_import.py`（TikHub 外部付费 API）整条链路无任何 reserve/charge 调用；`app/character_image_generation.py:586-630` 只记上游成本台账，不碰钱包。
- **影响**：商业化后客户按张/按分钟白嫖，供应商成本全部平台承担；与"按量计费"宣传直接矛盾。**这是每天都在发生的确定性亏损**。
- **修复方向**：四条链路接入与视频同构的 RESERVE/SETTLE/RELEASE（按张/按分钟档位）；短期可先加客户配额。与既有 `api_price_catalog` 蓝图（全栈分析报告 §9.5）合并实施。

### P0-2 报价口径与实扣口径相差约 80 倍——大规模"多扣费"客诉温床
- **证据**：`GET /api/generation/price-quote` 按 `operation_cost_rates.external_price_768p/2k`（种子值 12/20 分/秒，`scripts/reconcile_customer_billing.py:79-89`）报价（`app/generation.py:6858-6889`）；实扣为 1 credit/秒、credit 售价默认 1000 分（`app/settings.py:69-78,340-358`），充值 `credits = amount_fen // charged_unit_price_fen`（`app/recharge_routes.py:206-207`）。页面报 0.12 元/秒，实扣 10 元/秒。
- **影响**：客户按页面报价理解会产生大规模退款争议；利润报表收入也按 12/20 分/秒折算（`migrations/058`、`app/admin_profit_routes.py:274-348`），与钱包实收严重脱节。
- **修复方向**：报价/实扣/利润折算三套价格源统一为同一张价表 + 一致性告警；报价端点改读实扣口径。

### P0-3 支付掉单无自动补偿，客户无任何自助出路
- **证据**：唯一自动入账路径是回调 `app/payment_routes.py:50-92`；主动查单只有管理端手工单笔 `POST /control/recharge-orders/{order_no}/sync`（`app/payment_routes.py:104-216`）；客户侧订单查询只读本地库（`app/recharge_routes.py:534-565`）；无定时 sweep、无对账任务（`app/ops_metrics.py` 纯观测）。
- **影响**：ZPay 回调丢失 → 用户已付款、余额不到账，只能干等或找人工，直接形成资损客诉与信任损失。
- **修复方向**：定时任务对超 N 分钟仍 PENDING 的订单批量调 `ZPayOrderQueryClient` 补单（复用 `confirm_recharge_payment` 幂等性）；客户端订单页加"我已支付，立即查询"按钮。

### P0-4 付费成片从不落自有 COS 存储，质检从未执行——供应商 URL 过期即用户资产永久丢失
- **证据**：PG lane 全部走 `finalize_generation_direct_result` 直接置 `archive_status='DIRECT'`（`app/generation.py:5135-5187`；worker 调用点 `app/generation_worker.py:863-868,1046-1069`）；`storage.archive_result`（`app/storage.py:310-323`）在生产无任何调用；质检恒为 `quality_status="NOT_REQUIRED"`（`app/generation_worker.py:1053-1057`），`inspect_generated_video_quality`（`app/generation.py:6415`）成死代码；ARCHIVE_FAILED 重试机制（`app/generation.py:4420-4494`）在 PG lane 无初始触发点（循环依赖）。
- **影响**：与产品承诺"COS 归档质检"直接不符；用户付了钱的视频在供应商 URL 过期后永久不可访问——**最接近资损级的问题**。
- **修复方向**：在 ARCHIVING 步骤真实执行 download→COS put→质检（复用现成 `_retry_archive` 机制）；至少先加 DIRECT→归档的后台补录 job。

### P0-5 商用合规前提缺失——按自家红线本不应开放公网注册
- **证据**：`docs/上线前整改工作清单-2026-09-02.md:75` LEGAL-01（用户协议/隐私政策/AI 深度合成标识/备案）[EXT] 未做；`:44` 自设红线"无用户协议/隐私政策不得开放公网客户注册"；代码无协议版本接口、无账号注销/数据导出/删除端点（全库 grep 无对应路由）。
- **影响**：个保法下人脸/声纹数据的删除权无技术承载；即便带病上线也有合规硬伤。
- **修复方向**：协议版本下发接口 + 账号注销与数据清理任务，列为商用前最小集。

### P0-6（已知在案）storage×3 回归已在 main——阻塞所有 PR 的 Linux 门
- **证据**：`test_storage_cross_instance` 出现 SESSION_TOKEN_REQUIRED 确定性失败（2026-09-11 第 14 轮巡查在案；`app/`与测试代码自 38ae06c 全绿时零改动，疑共享 fixture 跨文件干扰）。本次为静态排查未复跑测试，以巡查记录为准，需 PG 环境复现修复。
- **影响**：任何任务 PR 无法过 Linux 质量门。
- **修复方向**：PG 环境复现 → 定位 fixture 干扰源 → 修复或隔离。

## 三、P1 问题清单（高优先，共 13 项）

### 资金回收类（共同根因：异常路径全靠人工）

**P1-1 口播任务供应商侧失败后，预留 credit 永不自动释放**
- `app/oral_worker.py:652-681` 提交即置 `CHARGED`；vendor 返回失败只置 FAILED 不调 `finalize_oral_billing`（`app/oral_worker.py:840-877`）；`app/internal_billing.py:414-421` 对 FAILED+CHARGED 直接抛 invariant；清扫器明确排除该组合（`app/internal_billing.py:102-108`）。用户 1 credit 被无限期冻结，只能管理员人工对账（`app/oral_routes.py:510-577`）。
- **修复**：对 vendor 明确 FAILED 增加"未扣费"自动/半自动 RELEASE 通道。

**P1-2 生成任务 SUBMISSION_UNCERTAIN 无超时终态与自动对账**
- `app/generation.py:521-527` 任何网络抖动（超时/5xx）一律升级 SubmissionUncertain；`mark_task_submission_uncertain`（`app/generation.py:5217-5260`）不 enqueue 任何 reconcile；释放只能靠管理员确认（`app/generation.py:3409-3528`）或用户手动 reconcile（`app/generation_routes.py:848-886`）。最多 15 credit/任务无限期冻结，批次堆 NEEDS_ATTENTION。
- **修复**：无 provider_task_id 且未付费的不确定态引入有限次自动 reconcile（复用 `generation_reconcile_operations` 表 + 退避）；有 provider_task_id 的加 SLA 计时 + provider 反查。

**P1-3 悬挂预留（RESERVE 无终态）清理无调度，自愈靠人跑 CLI**
- `reconcile_dangling_billing_reservations` 在 app 内无任何调用方，仅 `scripts/reconcile_dangling_billing_reservations.py:65`；BILL-03 注释自认 worker 事务回滚可造成悬挂（`app/internal_billing.py:56-69`）。
- **修复**：挂进 worker 主循环或定时任务（函数已带 SAVEPOINT 隔离，可直接复用）。

### 链路可靠性类

**P1-4 口播 RUNNING 任务无轮询超时上限，公平队列槽位可被永久占死**
- `app/oral_worker.py:451-461` 对 WAITING/PROCESSING 一律 15s 后重试，无 max-poll-age（对比生成域有 2h 上限 `app/generation.py:165`）；`cancel_oral_task` 只允许取消 QUEUED（`app/oral.py:889-897`）。飞影任务卡死 → 该用户 `running_tasks_count` 恒为 1，**所有后续生成/口播任务永不调度**。
- **修复**：给 oral poll 加与生成域同构的最大轮询年龄 + 超时转不确定态并释放槽位。

**P1-5 同步 create+poll 的 90 分钟阻塞路径仍留在代码里（一触即炸的陷阱）**
- `MetasoH3Provider.create_image_to_video = submit + _poll_for_result`（`app/generation.py:503-505`，`max_poll_attempts=1080`≈90min 阻塞，`app/generation.py:627-630`）；600s 租约（`app/generation.py:155`）远小于 90min，一旦被调用 sweeper 会把在跑任务判成 uncertain。当前 metaso 走 submit-only 不触发，但属高危陷阱路径。
- **修复**：删除 `_poll_for_result` 或在 Provider 上禁用该方法，统一两阶段。

**P1-6 worker 单线程串行 + 同步长阻塞调用，一个慢任务饿住其他域**
- `run_forever_pg` 单循环（`app/generation_worker.py:1612-1624`）；ASR 同步 poll 90 次（`app/asr.py:261-270`）、analysis 240s（`app/analysis.py:227`）、图像 provider 240s（`app/first_frames.py:499`）均发生在两事务之间且无并发。一个 4 分钟拆解阻塞口播/生成推进；容量默认仅 2（`app/generation.py:6806`）。
- **修复**：按任务域拆 worker 进程/线程池，或 ASR 改 checkpoint 续步。

### 支付与对账类

**P1-7 PENDING 充值订单无过期关闭机制（僵尸单累积，与 P0-3 叠加）**
- 状态机无 TTL（`app/zpay_payments.py:14`），CLOSED 仅用户手动删除（`app/recharge_routes.py:568-616`）。
- **修复**：补单任务顺带将超龄未付订单置 CLOSED（`app/zpay_payments.py:136-157` 已允许 CLOSED 入账，语义安全）。

**P1-8 经营报表收入漏口播、成本漏 TikHub/分析——毛利双向失真**
- 收入只从 `wallet_transactions JOIN generation_tasks` 取 SETTLE（`app/admin_profit_routes.py:292-314`、`app/admin_dashboard_routes.py:158-186`），口播 SETTLE 挂 `oral_task_id` 不落 generation_tasks；TikHub/分析成本无记录（`app/operation_costs.py` 仅 generation/character_image/independent 调用）。看板却把 `video_analysis_*、first_frame_image` 列为必备费率（`app/admin_dashboard_routes.py:253-269`），口径自相矛盾。
- **修复**：收入口径覆盖全部 SETTLE 类型；成本口径覆盖全部有外部支出的调用。

**P1-9 计费秒数取请求档位，不校验实际输出时长**
- `billed_seconds = request.output_duration_seconds`（用户传参，`app/generation.py:200,2121-2148`）；实际输出秒数仅记成本不回冲（`app/operation_costs.py:176-251`）。请求 4s 实出 15s（用户赚）或反之（用户亏）均不校正，与供应商按实际输出计费形成毛利黑洞/客诉点。
- **修复**：结算时用 provider 回报秒数做偏差校验，超阈值补退或标记人工审。

**P1-10 口播改价配置与实扣脱钩**
- `oral_unit_price_fen`（`migrations/081`，管理可改）只写进展示字段 `estimated_cost_fen`（`app/oral.py:64-78,725-761`），实扣恒为 1 credit（`app/internal_billing.py:294-324`）。管理员调价后报价变了、扣费没变。
- **修复**：按 price/charged_unit_price 折算扣 credit，或删除该配置避免误导。

### 安全类

**P1-11 未鉴权封面端点可驱动服务端回源抓取与写库**
- `GET /api/viral/covers/{platform}/{video_id:path}` 无鉴权、无限流；`stored is None` 时回源抓取第三方封面并写库（`app/viral_routes.py:824-869`）。可被未认证攻击者滥用为带宽/成本攻击与间接 SSRF。
- **修复**：回源分支移到鉴权/限流之后。

**P1-12 ZPay 支付回调无速率限制、无失败审计**
- `app/payment_routes.py:50-92` 仅 MD5 验签 + pid 校验，无 `consume_rate_limit`、失败不留 `security_auth_failures`——偏离本仓其他认证面"限流+审计"标准。
- **修复**：回调加 IP 维度限流，验签失败写安全审计。

**P1-13 SQLite 业务残留分支违反"PG 唯一"红线**
- `app/viral_routes.py:213-226` `_open_worker_connection` 直接读 `VIDEO_REPLICA_DB_PATH` 绕过 `db_pg.resolve_database_config()` 闸门；同类 `app/media_routes.py:472`、`app/auth.py:64`；全仓 30+ 业务文件 `import sqlite3`。启动闸门能拦在线启动，但后台线程/CLI 直调会在客户环境静默落 SQLite。
- **修复**：DB_PATH 分支从业务路由删除，统一收敛到单入口。

## 六、产品视角补充判断

- **多租户/团队模型缺失**：角色只有 admin/auditor/customer，项目强 owner 单人（`app/permissions.py:238`）；"小团队客户"只能共享一个激活码+两设备+单在线，协作互相踢线。需明确目标客群，若含团队需子账号/席位设计。
- **无收据/发票字段**（`app/zpay_payments.py:14`），与 BILL-04 缺口联动。
- **无站内公告/通知/到期提醒通道**，运营触达为零（激活码绑定后永不过期 `app/activation_code_service.py:71-73`，暂无到期硬需求，但续费/召回触达能力为零）。

## 七、做得好的点（排查确认的优势，重构时勿破坏）

1. **余额并发安全教科书级**：全部条件原子 UPDATE + rowcount 校验（`app/internal_billing.py:222-242,746-758`、`app/zpay_payments.py:174-200`），余额数学上不可能为负。
2. **防双花结构性排除**：`idempotency_key` 全局唯一 + `(task_id, billing_round)` 部分唯一索引 + CHECK 形状约束（`migrations/057:43-124`、`migrations/073`）；`finalize_*` 幂等重放终态。
3. **会话围栏（fencing）设计一流**：早期快照 + 事务内 FOR UPDATE 重校验 + clock_timestamp 租约判定 + epoch/lease 全元组重比对（`app/customer_auth.py:101-189`、`app/customer_fence.py`）；两设备单在线互踢、登出即失效、suspend 原子传播全闭环，且绝不静默踢人。
4. **多实例抢占与锁序规范**：统一 FOR UPDATE SKIP LOCKED、明确锁序 capacity row→cursor→task（`app/generation.py:6825-6848`），12 个真 PG 集成用例覆盖公平队列。
5. **激活码全链路防护**：140 位 CSPRNG + keyed HMAC 存储（无明文列）+ 统一 400 防枚举 + 常量延迟封时序 + PG 共享限流 + 并发兑换行锁串行化。
6. **支付回调纵深防御**：验签→pid→金额强核对→channel 白名单→trade_no 跨单绑定→PAID 幂等回放，入账与订单同事务。
7. **管理端治理成熟**：写契约（confirm+reason+幂等快照）、append-only 审计触发器、scrypt+防枚举、auditor 严格只读、RBAC 严谨。
8. **密钥管理成熟**：Fernet 主密钥走 OS Keychain/DPAPI、版本化轮换、启动门禁 fail-closed（`app/bootstrap.py:244-304`）、可信代理/Host 校验钉死边界。
9. **PG 运行时护栏真实**：statement_timeout 5min、idle_in_transaction 60s、池上限 64、超时脱敏日志、存储键防路径遍历 fail-closed。
10. **价格快照先于扣费、创建即冻结**，改价不影响在途任务（`app/generation.py:2137-2152`）。

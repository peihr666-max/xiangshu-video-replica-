## 〇、已证伪的结论（勿按此排期）

首轮排查有 4 条结论错误，根因相同：**本仓库存在双泳道**
（客户泳道 `/api/customer/*` vs 内部泳道 `/api/*`；PostgreSQL 生产泳道 vs SQLite 开发泳道）。
每次 grep 撞到其中一个实现就当成唯一实现，未回查调用方与另一泳道。

### ✗ 证伪 1　「口播分身/声音克隆只收钱不记成本」

生产 PostgreSQL 泳道在 `generation_worker.py:1252` 统一建立成本记录：

```python
if resolved_oral_vendor is not None and prepared_oral.kind.endswith("submit"):
    oral_attempt_id = begin_source_attempt(conn, prepared_oral.record_id)
```

`endswith("submit")` 覆盖 `avatar_submit` / `voice_submit` / `task_submit`。
首轮只读了 `oral_worker.py:509` 的 callee 和 `generation_worker.py:436`
的 `_run_sqlite_oral_step`；后者是 SQLite 开发泳道，而 `accept_operation`
依赖 `pg_advisory_xact_lock`，**SQLite 泳道根本不计费**。

**13 个对客收费科目全部具备成本记录。**

### ✗ 证伪 2　「客户积分流水无法归因」

客户实际使用 `CustomerWalletPanel` + `GET /api/customer/wallet/transactions`
（`recharge_routes.py:967`），该接口**已返回 `service` / `service_name` /
`billing_operation_id`**，并支持 13 个科目的 `business=` 筛选。
`server/tests/test_usage_billing.py:96` 已有断言锁定。

首轮盯的 `WalletPanel` + `/api/wallet/transactions`（`wallet_routes.py`）
是内部运营泳道，`App.tsx:417-424` 按泳道二选一渲染。

### ✗ 证伪 3　「余额不足只显示通用报错」

后端 402 消息 `"积分不足，本次需要 X 积分。"` 经
`customerVisibleErrorMessage`（`api.ts:5341`）原样透传，用户能看到正确文案。
实际缺失的只是「去充值」按钮（见 B-4）。

### ✗ 证伪 4　「计费测试环境损坏」

误用 `scripts/dev-with-pg.sh` 包装 pytest 导致。该脚本强制注入
`VIDEO_REPLICA_DATABASE_URL` 指向未迁移的 `customer_v3_test`，
覆盖了测试夹具自建的专用迁移库。

**正确命令**（与 `package.json` 的 `test` 脚本一致）：

```bash
uv --cache-dir .uv-cache run --project server --locked \
  python -m pytest --rootdir server server/tests/test_usage_billing.py -q
```

实测 **49 passed**。跑计费测试**不要**加 `dev-with-pg.sh`。

## 一、A 级 · 已执行验证的问题

### A-1　报表把「零供应商调用」判为「零成本」，静默虚增利润

**证据**：独立探针，两个除 attempt 外完全相同的 `analysis` 请求
（售价 5 分/次、成本 3 分/次、同一充值批次因而收入可知）：

```
p3-with  attempts=1  revenue=5.00  cost=3.00  profit=2.00   ← 正确
p3-none  attempts=0  revenue=5.00  cost=0     profit=5.00   ← 虚增 150%

TOTALS   revenue=10.00  cost=3.00  unknown_cost_count=0
         profit=7.00  margin=0.7     ← 真值应为 4.00 / 0.4
```

**根因**：`billing_reports.py:118-122` 与 `:44-48` 的 `LEFT JOIN costs`——
无 attempt 时 `calls=0, known_cost=0, unknown_cost=0`，
于是 `cost_complete = True`，成本按 0 计入，利润照常算出。

**危害不在于当前有漏记**（13 个科目均已覆盖），而在于**失败模式是静默的**：
将来任何新科目漏挂 attempt，报表不会报错、不会标「待核对」，
而是直接给出 100% 毛利。`unknown_cost_count` 也不会升起。

**目标**：收费科目的成功请求若无任何 attempt，应判为成本待核对。

**改法**：`costs` 聚合后增加判定——operation 的科目
`customer_charge_allowed = True` 且 `state = 'SUCCEEDED'` 且
`attempt_count = 0` 时计入 `unknown_cost_count`，使 `cost_complete = False`。
需同步改两处：`operation_rows()` 的 `cost_fen` CASE 与 `statistics()` 的 `facts` CTE。

**验收**（TDD）
1. 先落回归基线：现有 49 条测试必须全绿且利润数值不变。
2. 写 RED 测试：复现上述 `p3-none` 场景，断言 `profit_fen is None`。
3. 改 SQL 转绿。

**风险**：中——改的是财务报表 SQL，回归基线必须先行。

## 二、B 级 · 已逐条执行验证（2026-09-17 补）

原为静态检索结论，现已全部跑探针验证，结果如下。
**5 条现象全部属实，但 B-5 的处置建议被推翻**。

先确认一件基础事实：本应用的路由是懒注册的（`app.routes` 里是
`_IncludedRouter` 包装，直接遍历只能看到 9 条内建路由）。
展开后真实路由共 **348** 条，下列端点均确认可达：

```
GET/PUT /api/control/settings/rates          GET /api/control/settings/rates/history
GET     /api/control/profit/overview         GET /api/control/profit/overview.csv
GET     /api/control/profit/costs            GET /api/control/profit/costs.csv
PUT     /api/control/profit/daily-price
GET     /api/customer/billing/catalog        GET /api/customer/billing/quote
```

枚举方式（`app.routes` 直接遍历会漏）：

```python
def walk(routes):
    out = []
    for r in routes:
        if type(r).__name__ == "_IncludedRouter":
            out.extend(walk(r.original_router.routes))
        elif getattr(r, "methods", None):
            out.append(r)
    return out
```

### B-1　✅ 证实 — 旧费率表改价不生效，但仍是活写接口

**探针**：把 `operation_cost_rates.first_frame_image` 改成 777，
`billing_tariffs.first_frame.unit_cost_fen` 设为 5，
再跑 `begin_operation_cost(subject="first_frame_image")` + `complete_operation_cost(usage=2)`：

```
实际记账 unit_price_fen = 5.000000，cost_fen = 10.00000000
→ 读的是 billing_tariffs，operation_cost_rates 是死数据
```

同时 `GET /api/control/settings/rates` 仍会把那个不生效的 **777** 回显给管理员。
即：改价返回 200、写审计日志、页面显示新价，**但计费按旧价走**。

| | 新（生效） | 旧（失效） |
|---|---|---|
| 表 | `billing_tariffs` | `operation_cost_rates` |
| 写接口 | `PUT /api/control/billing/tariff` | `PUT /api/control/settings/rates` |
| 前端 | `BillingRatesManager.tsx`（已挂载） | `RatesManager.tsx`（0 引用） |
| 计费读取 | `operation_costs.py:32` → `read_tariff` | 无 |

**下线的改动面比首轮估计大**：`server/tests/test_admin_rate_routes.py`
有大量测试依赖该路由；`test_customer_chain_e2e.py:141` 与
`test_sqlite_to_postgres.py:1078` 引用该表；`test_cw056_supported_head_matrix.py:185`
把它列入支持矩阵。

### B-2　✅ 证实 — 两套利润口径看到的是不相交的数据

**探针**：同一笔已交付且已扣费的 `analysis` 请求（售价 5 分、成本 3 分），
分别用新口径的 `statistics()` 和旧端点 `/api/control/profit/overview` 的原样 SQL 计算：

| | 收入 | 成本 | 利润 |
|---|---|---|---|
| 新 `/api/control/billing/statistics` | 5.00 | 3.00 | 2.00 |
| 旧 `/api/control/profit/overview` | **0** | **0** | **0** |

**根因**：旧口径收入侧
`JOIN generation_tasks t ON t.id = wt.task_id` —— 只认视频；
成本侧只读 `operation_cost_records` —— 只覆盖视频/分析/首帧/人物图。
且收入基准是**手工录入的 `daily_external_prices`**，而非真实充值折算。

两套口径不是"数字有偏差"，是**看的不是同一批事实**。

### B-3　✅ 证实 — 通用报价接口零调用（但不是功能缺口）

`/api/customer/billing/quote` 与 `/api/customer/billing/catalog` 确认可达，
客户端零调用；已排除动态 URL 拼接（`client/src` 无 `` `/api/customer/${...}` ``
或字符串拼接形式的调用）。

**客户并非看不到价格**：`/api/customer/pricing` 已被 `CustomerPricesPage`
（客户中心「功能价格」全表，13 个对客科目齐全）与 `FirstFrameSelection` 使用；
视频、口播另有专用报价端点。

因此这是**死代码清理**，不是功能缺口。优先级低于首轮判断。

### B-4　✅ 证实，且比首轮描述更差

后端 402 抛出点共 3 处：`usage_billing.py:84`（影响全部 13 个科目）、
`generation.py:1933`（视频）、`oral_routes.py:440`（口播）。

前端只有视频路径有充值引导：`ProjectDetailFlow.tsx:531` 与
`useGenerationDrafts.ts:1163` 调 `setInsufficientBalance()`，
渲染于 `ProjectDetailFlow.tsx:748` / `GenerationComposer.tsx:50`。

**新发现**：
- `AnalysisWorkspace.tsx` 有 `onRecharge` 形参，但只是**透传**给
  `GenerationComposer`（`:972`），分析自身不处理 402。
- 口播有专门的 402 抛出点，`client/src/studio/**` 却**零处理**。

### B-5　⚠️ 现象属实，但「移除」的建议被推翻

**现象证实**：两个科目在管理端费率页可见可配（客户侧不可见），
给 `analysis_repair` 写入成本价 42 成功落库，但全仓零调用点，
永远不会产生 `billing_attempts` 行。已排除动态构造
（科目名只有 `f"video_generation_{suffix}"` 一处 f-string，与本科目无关）。

**推翻移除建议的证据**——`docs/evidence/ui-typography-brand/review-fixes.md:15`：

> 新内部计量项目 `analysis_repair_deepseek` 不向用户新增收费；
> 旧 `analysis_repair` 及历史供应商成本快照保留。

即**保留是刻意的**，为了让历史 `billing_attempts` 行仍有对应的目录项。
数据库 CHECK 约束也显式点名了它：

```sql
CHECK ((service <> ALL (ARRAY['quality_inspection','analysis_repair'])) OR (NOT enabled))
```

移除的实际影响：`control_routes.py:673` 与 `operation_costs._rate` 都有
`in SERVICES` 保护不会崩，但 `billing_catalog.read_tariff` 对未知科目
**抛 `ValueError("未知计费科目")`**，历史数据的读路径会碎。

**改为建议**：不移除，而是在管理端费率页把这类科目标注为
「历史科目 · 已停用」，避免运营误配成本价后以为生效。

附带发现：`analysis.py:1007` 的 `_provider_response_ref(raw, repaired)`
唯一调用点（`:493`）永远传 `None`，`repaired_response` 形参是死参数，可清理。

#### 关于 #3：只抽谓词，不抽 hook

原计划的 `useInsufficientCredits` 没有做。两类界面的承接方式本就不同——

运营误配的风险远低于原判断。要"标注"反而得先把它们加回 UI，适得其反。

#### ✗ 撤销 #6：保留 `/api/customer/billing/quote`

## 七、生产数据交叉验证

```sql
SELECT o.service, count(*) AS ops, count(a.id) AS attempts,
       sum(o.charged_credits) AS credits
FROM billing_operations o
LEFT JOIN billing_attempts a ON a.operation_id = o.id
WHERE o.state = 'SUCCEEDED'
GROUP BY o.service ORDER BY 2 DESC;
```

`attempts = 0` 且 `credits > 0` 的行即被 A-1 静默虚增利润的科目。
按本文结论该查询应返回空集；若不为空，说明已有真实虚增发生。

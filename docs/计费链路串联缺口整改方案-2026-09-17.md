## 〇、已证伪的结论（勿按此排期）

首轮排查有 4 条结论错误，根因相同：**本仓库存在双泳道**
（客户泳道 `/api/customer/*` vs 内部泳道 `/api/*`；PostgreSQL 生产泳道 vs SQLite 开发泳道）。
每次 grep 撞到其中一个实现就当成唯一实现，未回查调用方与另一泳道。

### ✗ 证伪 1　「口播分身/声音克隆只收钱不记成本」

生产 PostgreSQL 泳道在 `generation_worker.py:1252` 统一建立成本记录：

```python
if resolved_oral_vendor is not None and prepared_oral.kind.endswith("submit"):
    oral_attempt_id = begin_source_attempt(conn, prepared_oral.record_id)
```

`endswith("submit")` 覆盖 `avatar_submit` / `voice_submit` / `task_submit`。
首轮只读了 `oral_worker.py:509` 的 callee 和 `generation_worker.py:436`
的 `_run_sqlite_oral_step`；后者是 SQLite 开发泳道，而 `accept_operation`
依赖 `pg_advisory_xact_lock`，**SQLite 泳道根本不计费**。

**13 个对客收费科目全部具备成本记录。**

### ✗ 证伪 2　「客户积分流水无法归因」

客户实际使用 `CustomerWalletPanel` + `GET /api/customer/wallet/transactions`
（`recharge_routes.py:967`），该接口**已返回 `service` / `service_name` /
`billing_operation_id`**，并支持 13 个科目的 `business=` 筛选。
`server/tests/test_usage_billing.py:96` 已有断言锁定。

首轮盯的 `WalletPanel` + `/api/wallet/transactions`（`wallet_routes.py`）
是内部运营泳道，`App.tsx:417-424` 按泳道二选一渲染。

### ✗ 证伪 3　「余额不足只显示通用报错」

后端 402 消息 `"积分不足，本次需要 X 积分。"` 经
`customerVisibleErrorMessage`（`api.ts:5341`）原样透传，用户能看到正确文案。
实际缺失的只是「去充值」按钮（见 B-4）。

### ✗ 证伪 4　「计费测试环境损坏」

误用 `scripts/dev-with-pg.sh` 包装 pytest 导致。该脚本强制注入
`VIDEO_REPLICA_DATABASE_URL` 指向未迁移的 `customer_v3_test`，
覆盖了测试夹具自建的专用迁移库。

**正确命令**（与 `package.json` 的 `test` 脚本一致）：

```bash
uv --cache-dir .uv-cache run --project server --locked \
  python -m pytest --rootdir server server/tests/test_usage_billing.py -q
```

实测 **49 passed**。跑计费测试**不要**加 `dev-with-pg.sh`。

## 一、A 级 · 已执行验证的问题

### A-1　报表把「零供应商调用」判为「零成本」，静默虚增利润

**证据**：独立探针，两个除 attempt 外完全相同的 `analysis` 请求
（售价 5 分/次、成本 3 分/次、同一充值批次因而收入可知）：

```
p3-with  attempts=1  revenue=5.00  cost=3.00  profit=2.00   ← 正确
p3-none  attempts=0  revenue=5.00  cost=0     profit=5.00   ← 虚增 150%

TOTALS   revenue=10.00  cost=3.00  unknown_cost_count=0
         profit=7.00  margin=0.7     ← 真值应为 4.00 / 0.4
```

**根因**：`billing_reports.py:118-122` 与 `:44-48` 的 `LEFT JOIN costs`——
无 attempt 时 `calls=0, known_cost=0, unknown_cost=0`，
于是 `cost_complete = True`，成本按 0 计入，利润照常算出。

**危害不在于当前有漏记**（13 个科目均已覆盖），而在于**失败模式是静默的**：
将来任何新科目漏挂 attempt，报表不会报错、不会标「待核对」，
而是直接给出 100% 毛利。`unknown_cost_count` 也不会升起。

**目标**：收费科目的成功请求若无任何 attempt，应判为成本待核对。

**改法**：`costs` 聚合后增加判定——operation 的科目
`customer_charge_allowed = True` 且 `state = 'SUCCEEDED'` 且
`attempt_count = 0` 时计入 `unknown_cost_count`，使 `cost_complete = False`。
需同步改两处：`operation_rows()` 的 `cost_fen` CASE 与 `statistics()` 的 `facts` CTE。

**验收**（TDD）
1. 先落回归基线：现有 49 条测试必须全绿且利润数值不变。
2. 写 RED 测试：复现上述 `p3-none` 场景，断言 `profit_fen is None`。
3. 改 SQL 转绿。

**风险**：中——改的是财务报表 SQL，回归基线必须先行。

## 三、待业务拍板（不在本分支）

### COS 与支付通道成本未建模

- `billing_routes.py:122` **强制** `cos` / `zpay` 的 `unit_cost_fen` 只能为 0。
- 无任何地方为 COS 存储/流量或支付手续费创建 attempt。
- `wechat_native` 是正式 provider（`settings.py:189`）但无计费科目。
- 充值按 `amount_fen` 全额计收入（`recharge_routes.py:224`），手续费无扣减。

**这是口径不是 bug**：现有「利润」明确等于「对客收入 − 上游 API 成本」。
问题在于报表未标注这一边界，容易被读作净利。

**需拍板**
1. COS 成本：按月账单摊分（简单，不可按客户归因）还是按请求实时记账
   （可归因，但要给每次 `put_object` 挂 attempt，影响热路径）？
2. 支付手续费：按笔实时扣减（需为 `wechat_native` 补科目）还是月度报表层扣减？

## 七、生产数据交叉验证

```sql
SELECT o.service, count(*) AS ops, count(a.id) AS attempts,
       sum(o.charged_credits) AS credits
FROM billing_operations o
LEFT JOIN billing_attempts a ON a.operation_id = o.id
WHERE o.state = 'SUCCEEDED'
GROUP BY o.service ORDER BY 2 DESC;
```

`attempts = 0` 且 `credits > 0` 的行即被 A-1 静默虚增利润的科目。
按本文结论该查询应返回空集；若不为空，说明已有真实虚增发生。

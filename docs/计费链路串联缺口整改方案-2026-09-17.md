## 〇、先行结论修正

首轮排查曾判定「口播分身创建 / 声音克隆只收钱不记成本」为 P0 漏洞，**该结论错误，已撤回**。

生产 PostgreSQL 泳道在 `generation_worker.py:1252` 对所有 `*_submit` 类型统一建立成本记录：

```python
if resolved_oral_vendor is not None and prepared_oral.kind.endswith("submit"):
    oral_attempt_id = begin_source_attempt(conn, prepared_oral.record_id)
```

`endswith("submit")` 覆盖 `avatar_submit` / `voice_submit` / `task_submit` 三种。首轮只读了
`oral_worker.py:509` 的 `_perform_submission` 与 `generation_worker.py:436` 的
`_run_sqlite_oral_step`，后者是 SQLite 开发泳道；而 `accept_operation` 依赖
`pg_advisory_xact_lock`，**SQLite 泳道不参与计费**。

**复核结论：13 个对客收费科目全部具备成本记录，无漏记。**

## 一、整改清单

优先级定义：P0 = 直接影响客户体验或对账可信度，必须本轮修；
P1 = 有误导风险或半截功能，本轮修；P2 = 清理项，可本轮可延后。

### P0-1　客户积分流水无法归因

**现状**

`usage_billing.py:210-212` 写流水时只对视频和口播回填任务号：

```sql
CASE WHEN service IN ('video_768p','video_2k') THEN source_id END,  -- task_id
CASE WHEN service='oral' THEN source_id END                          -- oral_task_id
```

其余 11 个科目（分析、改写、转写、人物图、首帧、分身克隆、声音克隆、链接解析、
提示词优化、爆款数据、源画面质检）两字段均为 NULL。

`wallet_routes.py:99` 的 `WalletTransactionResponse` 已声明 `service`、`service_name`、
`billing_operation_id` 等字段，但 `list_wallet_transactions` 的 SELECT **未查询这些列**，
`WalletTransactionResponse(**dict(row))` 使其恒为 `None`。

对照：管理端同类接口 `control_routes.py:642` 已关联 `billing_operations.service` 并映射中文名。
**管理员能归因，客户不能。**

**影响**：客户在 `WalletPanel.tsx:298` 只能看到「消费 / -14」，无科目无单号，无法自查，
直接转化为客服工单。

**目标**：客户流水每行可读出科目中文名；可归属到任务的仍显示任务号。

**改法**
1. `wallet_routes.py` 的 SELECT 增加 `billing_operation_id`，并以子查询关联
   `billing_operations.service`（照搬 `control_routes.py:642` 的写法，含 `user_id` 同源约束）。
2. 用 `billing_catalog.SERVICES[service].name` 映射 `service_name`，未知科目返回 `None`。
3. `WalletPanel.tsx` 流水表增加「项目」列，优先显示 `service_name`，回退到
   `transactionTypeLabel(type)`。

**不改**：不回填历史流水的 `task_id`；旧数据 `billing_operation_id` 为 NULL 时
`service_name` 显示为空，不臆造。

**验收**
- 后端：新增测试断言 `rewrite` / `link_resolution` 类流水返回非空 `service_name`。
- 前端：`WalletPanel.test.tsx` 断言渲染出科目名。

**风险**：低。`WalletTransactionResponse` 字段已在 OpenAPI schema 中声明，
客户端类型由 `components["schemas"]` 生成，**无需改前端类型或重跑 `generate:api`**。

### P1-5　报表将「零调用」判定为「零成本」

**现状**

`billing_reports.py:118-122` 与 `billing_reports.py:44-48`：

```sql
LEFT JOIN costs c ON c.operation_id = o.id
-- 无 attempt 时：calls=0, known_cost=0, unknown_cost=0
-- → 判定「成本齐全」→ 成本记 0 → 毛利 = 全额收入
```

**当前无线上实例**（13 个科目均有 attempt 覆盖），属结构性隐患：
将来任何新科目漏挂 attempt，都会以「100% 毛利」的形式静默虚增利润，而非报错。

**目标**：漏挂 attempt 时报表显示「待核对」而非「零成本」。

**改法**：在 `costs` 聚合后增加判定——若 operation 的科目
`customer_charge_allowed = True` 且 `state = 'SUCCEEDED'` 且 `attempt_count = 0`，
则计入 `unknown_cost_count`，使 `cost_complete = False`。

需同步改两处：`operation_rows()` 的 `cost_fen` CASE 与 `statistics()` 的 `facts` CTE。

**验收**：TDD——先写一条「成功但无 attempt 的收费 operation」的测试，
断言 `profit_fen is None`，确认其当前失败（RED），再改 SQL 转绿。

**风险**：中。改的是财务报表 SQL，必须有回归测试锁定既有行为
（既有 12 个科目的利润计算结果不得变化）。

### P2-7　余额不足的充值引导只覆盖视频

**现状**（已修正首轮表述）

后端 402 消息 `"积分不足，本次需要 X 积分。"` 会经
`customerVisibleErrorMessage`（`api.ts:5341`）原样透传，用户**能看到正确文案**。

缺的是专门 UI：只有 `ProjectDetailFlow.tsx:531` 与 `useGenerationDrafts.ts:1163`
会 `setInsufficientBalance({neededCredits, balanceCredits})` 触发充值面板。
其余 11 个科目触发 402 时只有一行错误文字，没有「去充值」入口。

`BILLABLE_DURATION_REQUIRED`(422)、`BILLING_REQUEST_CONFLICT`(409) 前端零特化处理。

**改法**：抽取共用 `useInsufficientCredits()` hook，在 P1-4 接入报价的两个科目上一并挂载。
其余科目随后续迭代推进。

**风险**：低。

### 待决策（不在本分支）　COS 与支付通道成本未建模

**现状**

- `billing_catalog.py:44-45` 定义 `cos` / `zpay` 科目，但 `billing_routes.py:122`
  **强制其 `unit_cost_fen` 只能为 0 或空**。
- 全仓无任何地方为 COS 存储/流量/请求数，或支付渠道手续费创建 attempt。
- `wechat_native`（微信原生支付）在 `settings.py:189` 是正式 provider，**连科目都没有**。
- 充值按 `amount_fen` 全额计为收入（`recharge_routes.py:224`），渠道手续费无扣减。

**这不是 bug，是口径**：现有「利润」明确等于「对客收入 − 上游 API 成本」，
不含存储与支付通道。问题在于报表未标注这一口径边界，容易被读作净利。

**需要拍板的两点**
1. 成本口径：COS 按月账单摊分，还是按请求数 × 单价实时记账？
   前者简单但不能按客户归因；后者要给每次 `put_object` 挂 attempt，改动面大且影响热路径性能。
2. 支付手续费：按笔费率实时扣减（需为 `wechat_native` 补科目），还是仅在月度报表层扣减？

**本分支处理**：仅在 `billing_reports.statistics()` 的 `basis` 文案中补一句口径说明
（「不含云存储与支付通道成本」），让管理端页面自我澄清。实际建模另开提案。

## 五、生产数据交叉验证（建议执行）

静态排查的结论应由真实数据复核一次：

```bash
psql "$VIDEO_REPLICA_DATABASE_URL" -c "
SELECT o.service,
       count(*) AS ops,
       count(a.id) AS attempts,
       sum(o.charged_credits) AS credits
FROM billing_operations o
LEFT JOIN billing_attempts a ON a.operation_id = o.id
WHERE o.state = 'SUCCEEDED'
GROUP BY o.service
ORDER BY 2 DESC;"
```

`attempts = 0` 且 `credits > 0` 的行即为漏挂成本的科目。
按本文结论，该查询应返回空集；若不为空，说明存在静态排查未覆盖的路径。
